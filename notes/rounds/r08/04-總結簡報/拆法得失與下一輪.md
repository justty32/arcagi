## 5. 得失

**得**
- 量具更嚴：盲測 H24、train 留一＋MDL 門取代 test／S5 神諭濾網、logcost 封頂、跨題 bootstrap、`pool-noG1`／`pool-rand32` 對照——「沒學到」這件事這輪能被確定地量出來，不是雜訊。
- 第一次看到「練習池 → 積木 → 跨題共用」走通（foot32：8 積木、`transpose` 6 題共用、H24 +1）。
- 空樹語言有了 C++ 引擎（S1）和 golden 原語測試，r09 加大預算不必再靠 Python。

**失（否定結果）**
- 使用者指定的主題集中，在挑到「空樹碰不到的主題」時完全沒料；主題要有立足點才有用。
- 有料時積木也不一定轉移：foot32 長的是幾何／鏡像積木，L16 需要的是鄰接、區域、兩半——**練習池的主題要跟計分組的缺口相連**，不能只看有沒有立足點。
- 新積木會干擾舊解（beb8660c 在 foot32 掉了）：積木入庫沒有「不拖慢已解題」的檢查。
- meta 再次全部不採用：旋鈕都不是瓶頸；拆法開關、守門門檻、主題挑法這些真正有影響的東西仍是 agent 手調。

## 6. 下一輪方向（r09）：使用者 11-08 晚七條為主

原話全文 → [r09-使用者七條原話](../r09-使用者七條原話.md)。**r09 規劃等 aos alt-fable Q7「錘子設計圖 v1」（`~/repo/simple_tools/aos/proto8/thinking/2026-11/08/alt-fable/out/`）出來再定稿，本隊長不開 r09。** 以下是 r08 結果對每條的對照，給 r09 規劃當料：

1. **錘子造錘子（意見 5）**：「agi本質上是工程問題……我們先造一把lv1錘子……去打造一把lv2錘子……所以現在的重點是，這把錘子的設計圖。」→ r08 的錘子（`grow/` 學習循環）在 meta 層 5 回合全不採用：lv1 錘子改不動自己。設計圖要先回答「錘子的哪些部件是可被搜尋的節點」。
2. **非 LLM 節點、產業園區（意見 1）**：「所謂agent，爲何要限制爲LLM agent？……任何一個函數都可以這樣」→ r08 的拆法（halves、nest、map、zip_pos…）、G1 門、主題挑法本來就是函數節點；可按 2D／list／改進分區。
3. **便宜的審查與改進（意見 2）**：固定統計程式 → 符號迴歸 → 專用替換程式，LLM 最後 → r08 的 G1 門（留一＋MDL）就是「固定統計程式」型審查；下一步讓它的門檻也被搜（符號迴歸／暴力）。
4. **固化（意見 3）**：agent → tool → 程式 → r08 裡 agent 手做的三件事——加拆法（halves）、挑主題（foot32 規則）、放寬門（D-r8-19）——都可以固化成可搜尋的程式節點。
5. **epoch 往上／往下長（意見 4）**：「當發現最近幾次改進都沒有突破，那就拉一個新節點出來擺在上面」「往下就是拆開來」→ r08 正是「meta 連續不採用」的停滯點：往上＝改判準本身（D-r8-23 的兩段判準）、往下＝把卡住的 L16 題拆成子目標（C++ `seed-sub` 已能批次吃子問題）。
6. **暴力匹配優化節點樹本身（意見 6）**：「你要用這套暴力型模式匹配，去優化我們的節點樹，不管是審查或改進或是本體，全都要」→ r08 只有本體（程式）被暴力搜；審查（G1 門、守門門檻、CRN 判準）與改進（拆法集合、主題挑法、預算排程）仍手調。S1 的 C++ 引擎（快 12～22 倍）讓「在節點樹設定空間上暴力搜」付得起。
7. **活的樹、可干預（意見 7）**：學習迴圈要成為試驗場裡活的 aos 樹，使用者能 cd 進去看、對節點發訊息 → 現在 `aos/seedlib`、`aos/meta` 是靜態資料夾，`grow/` 是一次性腳本；要改成常駐、有節點收件匣的樹。

另外留給 r09 的技術項（非主方向）：練習池主題要跟 L16 缺口相連（不只立足點）；積木入庫加「不拖慢已解題」影子檢查；二維位置拆法；守門剩 9 題（`stamp_key`、移動＋裁切、寫死 colormap）；G2 re-arc 片段、G3 殘差診斷。
