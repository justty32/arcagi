## 1. 目標與使用者前提（原話整理）

- 使用者：「就是拿我們這套 aos 體系去嘗試解 arcagi」。**符號邏輯**解 ARC-AGI-1；LLM 只用來找規則、寫程式、蒸餾，最終解題靠確定的程式；**神經網路盡量不用**。可暴力吃 CPU、可寫 CUDA（RTX 5060 Ti 16GB）。
- 遠期：ARC-AGI-1 是「種子」，要慢慢長大到能代替 LLM 當思考驅動 → **能累積、能自我長大的結構**比一次性分數更重要，但分數仍是量尺。
- **本輪主軸（使用者 11-08 12:05 原話，r02 只做了最小版）**：「試試看“優化產生積木”這件事。積木的本質是模式匹配，模式難道只有這些幾何嗎？一段程式輸出true,json object，也可以算模式對吧，或是一個公式如x=y的2次方，這樣甚至可以超越大小」。另一主軸：**用 aos 體系**（積木＝資料夾程式、node-pool 記帳、covered 壓縮）。
- 方向問題不停線：隊長代定、記代定清單，使用者回來翻案。

## 2. 不可違反的約束

| 約束 | 說明 |
|---|---|
| 成績以 **evaluation 400 題**為準 | training 有 re-arc 現成解答（洩漏風險），只當開發集；**產生／評分積木只能用 training** |
| 不用神經網路；**不新增 Python 依賴** | 純 stdlib（無 numpy）。C++／CUDA 可另開子資料夾經 `--external` 接 |
| 機器安全 | CPU 批次 `nice -n 19`、≤12 worker、單批 ≤16GB、顯存 ≤12GB、swap 512MB；同時只跑一條全量評測 |
| 額度緊 | 本輪約 **3 條 opus 線×1～1.5 小時**＋全量 training、evaluation 各一次為原則；aos-llm 要額度 |
| aos repo **只讀** | 在 arcagi 的 `aos/` 試驗場做，用本機 aos 指令；不跑 install.sh |
| 程式碼規矩 | `src/arcagi/<領域>/`，單檔 >300 行拆；pytest；commit 附 evaluation 改前／改後題數，退步列原因 |

## 3. 現況（r01＋r02 已有）

- 成績：**evaluation 28/400**、training 79/400（r01 21／57）；退步 0；全量 evaluation 約 140 秒、每題最長 1.8 秒（預算 5 秒遠沒用完 → **瓶頸是積木覆蓋，不是算力**）。
- 搜尋：逐層 BFS 到 3 步、觀察等價去重、參數從範例推、最短程式勝出；終端學習器（換色表、鄰域規則表、物件換色表）不佔深度；標記色 10。程式＝JSON 列表。
- 積木：整張網格原語 18＋物件「選擇器＋動作」6（只當第一步）＋格線 4＋巨集 4＋**自動產生的謂詞 60 live／40 covered**（`blocks/gen_predicates.py`：1～2 字面的 eq／gt／lt／rank／AND，在 training 評分，0 分不落地）。ae58858e 是自動謂詞 `size > 3` 解的。
- aos：`aos/blocks/<名>/`（`_metainfo.json`＋`_entry`，`aos-exec` 可單叫）；`aos/solver/_entry`（external 端到端）；`aos/pool/` 記帳 epoch 0～2（解一題 1000、頂層留 20%、80% 按選中程式**直接**引用分紅、房租 100、連 3 epoch 0 → 建議退休）；產生器節點 `_gen/pred_combiner` 抽謂詞分紅的 20%。
- r02 已定的四型表示（fable 增補）：共用外殼 `{"kind":pred|extract|formula|transform,"in","out","body"}`，body 是 S 式 JSON；抽取結果以 `$extract:` 當變換參數、公式先定輸出尺寸。**抽取型、公式型還沒施工**。

## 4. 失分在哪（隊長重算，r02 報告）

| 切片 | evaluation | training |
|---|---|---|
| 同大小 | 8/270 | 37/262 |
| 輸出比輸入小 | 16/94 | 31/101 |
| 其他（變大／混合） | 4/36 | 11/37 |
| 過 train 但答錯（背答案） | 12 | 20 |

**輸出尺寸**（非同大小的 130 題 evaluation）：尺寸固定 68 題（解 16）、整數倍放大／縮小 8 題（解 2）、**其餘 54 題尺寸隨輸入變化但不是簡單倍數（解 2）**——這 54 題是「公式型／抽取型」最直接的池子（例：輸出高＝物件數、輸出＝某物件的框）。

已知問題（r02 抽查）：
- **物件背景**用整格眾數色，同題不同 pair 會不一致 → training 有 53 題「謂詞分得開變／不變物件但沒轉成解」。謂詞選擇器目前只接換色，沒接刪／留／移動。
- **top-2 沒用**：搜尋停在第一個有解的深度，evaluation 只 3 題有不同輸出的第二候選。
- **帳**只看直接引用 → flip_ud、rot90 等基礎幾何被「建議退休」（未執行）。

## 5. 本輪候選（r02 隊長建議；**供選擇、非定案**）

| 案 | 內容 | 預期 evaluation 增量 | 跟主軸的關係 |
|---|---|---|---|
| C1 修物件背景 | 同題一致的背景色（所有 pair 共同眾數／邊框色）；謂詞選擇器擴到刪／留／移動／延伸 | +2～5（同大小） | 讓已產生的謂詞積木真的用上 |
| C2 抽取型積木＋產生器 | 抽取＝grid→JSON（物件清單、計數、顏色直方、框、唯一物件）；自動枚舉抽取式，評分＝在 training 上「抽出的值能解釋輸出某屬性」的題數；結果當變換參數（`$extract:`）或直接輸出（例：裁出被選物件、畫出計數條） | +2～6 | 使用者「json object 也是模式」 |
| C3 公式型積木＋產生器 | 輸出尺寸／數量＝f(輸入特徵) 的小式子枚舉（`h_out=a·x+b`、`x·y`、`x²`、max／min，x 取格高寬、物件數、顏色數、最大物件高寬…）；用途：(a) 搜尋剪枝（尺寸不符的分支丟掉）、(b) 生成類原語直接用（建新畫布、鋪 n 次） | +1～4，且讓搜尋可以更深 | 使用者「公式 x=y² 可超越大小」 |
| C4 同深度多解＋投票 | 到達有解深度後收完該深度（或多一層）的全部解，按輸出分組投票，第二名進 top-2；學習器背答案的降權 | top-2 +1～4 | 降背答案 |
| C5 帳的修正 | `essential` 名單；巨集內引用按展開分紅；產生器節點記成本（產生耗時） | 0（結構） | aos node-pool 完整度 |
| C6 aos-llm 小樣本 | 20 題未解題，LLM 寫四型 JSON → 執行器驗 train，量通過率；`aos-llm ask` 經 llm-kernel（本機 daemon 在跑） | 不確定 | 「LLM 找規則、程式驗證」；**額度緊，可延後** |
| C7 元優化雛形 | 多個產生器（謂詞／抽取／公式）都是節點，帳決定下一輪給誰多預算 | 0（結構） | 「優化產生積木的過程」的上一層 |

- 公開經驗：icecuber 式手寫 DSL（約 140 變換、深度 3～4、C++）私有約 20%；公開 evaluation 上 DSL 搜尋一般 10～25%。

## 6. 要規劃者決定的方向問題

1. 本輪範圍：§5 選哪幾案、先後、分幾條線（≤3 條同時）；**驗收數字**（evaluation、同大小、training 下限與目標；每題時間；過 train 答錯上限）。
2. 抽取型與公式型的**產生器**怎麼設計：枚舉空間（特徵集、運算子、深度）、怎麼評分（training 上能解釋幾題）、怎麼防背答案（支持數、跨 pair 一致）、怎麼 covered／淘汰、怎麼接進搜尋（剪枝？參數來源？新原語？）。
3. 物件背景與謂詞動作擴充做到哪。
4. 多解投票：收多少、怎麼投、top-1 仍以最短為主嗎。
5. 帳：essential 名單誰決定、巨集分紅、產生器的成本怎麼記；本輪要不要真的執行退休。
6. LLM（C6）本輪碰不碰；碰的話怎麼省額度、量什麼。
7. 「優化產生積木的過程」本輪推進到哪一層（只做更多產生器？還是開始讓帳決定產生器預算？）。

## 7. 規劃產出格式（請照這個交）

範圍（一句）＋求解器與積木方法（新增產生器、原語／學習器、搜尋改動、選解法）＋**aos 接入**（接哪些、帳怎麼改）＋分線（檔案範圍、介面）＋驗收數字（evaluation／training、每題時間、測試、aos 可觀察驗收）＋對第 6 節每題的推薦答案（一句理由）＋第四輪預告。總長 ≤1800 字。
