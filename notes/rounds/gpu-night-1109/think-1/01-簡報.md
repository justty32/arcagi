### 2.4 N2 CUDA 評估器（`native/gpu/`，**不可改**，只能呼叫 `native/bin/gpusearch`）
- **語言**：程式＝長度 1..k 的格子步驟序列。`struct DStep{uint8_t op,a,b,pad;}`，`MAX_PAIRS=16`，`CELLS=900`。每題的字母表有 59～125 個步驟：D4 七種、upscale／tile／downscale（倍率 1..3）、mirror_tile、crop_bbox、gravity、fill_enclosed、split_overlay（2 軸×5 種運算）、self_tile、單對 colormap。train 全對且 test 輸出合法＝`exact`；形狀全對時可以配終端 `fit_colormap`；任何一步失敗或越界（>30）就丟棄。**這和活樹的 seed AST 語言是兩套。**
- **CLI**：`gpusearch --task FILE...|--tasks LIST [--data-dir DIR] [--mode gpu|cpu|both] [--depth 1..8] [--stop-first] [--budget SEC] [--samples N] [--out X.jsonl]`。每題輸出一行 JSON：程式空間大小、秒數、每秒候選數、兩側的解（以及兩側解集合是否一致）、最低成本的 arcagi JSON 程式（colormap 已填入）。train＋test 超過 16 對時標記 `too many pairs` 並跳過。
- **數字**：深度 ≤3、200 題、1.55e8 候選：GPU 每秒 6.89e7，CPU 6 緒每秒 1.55e6，**44.5×**，解集合 200/200 一致。深度 ≤4、12 題：GPU 每秒 3.01e8，**105×**。去重模式（CPU BFS 求唯一前綴×任意後綴）峰值每秒 9.2e8；深度 5 每題 0.1～6.5 秒，深度 6 每題 0.3～31 秒。**顯存約 512 MiB**（在 ≤2GB 限制內）。Python 重驗：train 19/19、抽樣 380/380；test 18/19（1 支是終端 colormap 過擬合）。
- host API：`gpu_open / gpu_load(task, inputs, targets, alpha) / gpu_set_prefixes / gpu_run(depth,start,count,sols,use_prefix,shared)`。
- **N3（另一條線，正在跑）**：`native/gpu/gp/`（未 commit）＋`native/bin/gpgp`（23:03 建置），在 N2 字母表上做 GPU 遺傳搜尋，`GpCfg{pop=65536, island=256, lmax=10, tourn=4, pcx .5, pmut .9, len_pen .002}`。這條線還在動，不要當成穩定介面；它的佔卡也是本施工要讓路的原因之一。

## 3. 文獻要點（標 ★＝可借用到 aos）
- **EvoGP**（2501.17168）：初始化、評估、交叉、變異全部放上 GPU，做族群級並行。樹用**線性前綴編碼**存成三陣列（`node_type/node_value/subtree_size`），補到最大節點數成為定形張量；子樹交換是統一的 GPU 原語，超長就判無效；CUDA kernel 註冊成 PyTorch 自訂算子；峰值 >1e11 GPops/s，對 SRGPU 快 304×、對 CPU Operon 快 18×。★ seed AST 可以照這個編碼做定長張量，在 GPU 上批次評估或變異；限制是要預設最大節點數。
- **SyMANTIC**（2502.03367）：互資訊特徵選擇＋逐層擴展特徵＋遞迴 L0 稀疏迴歸，從 1e4～1e10 個候選中挑低維描述子；複雜度用資訊論計算；PyTorch／GPU。★「先展開候選特徵、再做稀疏選擇」可用在單一功能節點的便宜改進（例如 gate 參數、成本公式）。
- **DreamCoder**（2006.08381）：Wake 階段用識別模型 Q(ρ|x) 排序枚舉；Sleep-Abstraction 最小化「庫＋重寫後語料」的描述長度；Dreaming 階段 replay 與 fantasy 各半。「庫降低深度、神經網路降低廣度」。文字編輯 3.7%→79.6%；成本很高（約一 CPU 年）。★ 活樹的睡眠造詞就是這個框架裡的 abstraction 步驟；還缺 recognition（廣度引導）。
- **Stitch**（2211.16605）：自頂向下合成帶洞的抽象，用壓縮效用上界做 branch-and-bound，不必真的重寫就能算出效用；比 DreamCoder 壓縮快 3～4 個數量級。限制：純語法比對、一次學一個。★ v4 M4 本來就打算用；可直接拿來對活樹 `solutions.jsonl`、`near_top` 和 trace 造詞，不經 LLM。
- **EvoNUDGE**（2411.05820）：GNN（3 層 GAT）對節點打 saliency，只擴展前 k 個節點；導引 GP，用庫做初始化＋子樹替換。t=6 時成功率 43.4%（GP 31.4%），總時間不到 GP 兩倍；訓練要 8 GPU×24h。★ 「小網路排序哪裡值得變異」＝符號＋神經混合的最小形；要注意訓練成本和圖變大後準度下降。
- **GridCoder**（2411.17708）：VLM 輸出 DSL token 機率（假設條件獨立，攤成位置×類別），依聯合機率枚舉後驗證；在 DSL 可解的 29 題上 79.3%（MCTS＋VLM 69%、只用 VLM 13.8%）；結構 OOD 10 題只解 1 題。★ 「每位置×原語的機率表」可以用 N2 的 DStep 字母表當類別，訓練一個很小的先驗；但泛化有限。
- 未找到 TensorGP、cuML GP 專篇。

## 5. 反省題（aos 體系的瓶頸／斷點；只列問題，不寫方案）

**R1 兩套語言、兩個世界。** 活樹的積木是 seed AST list 語言（`map/lam/append/reverse/$in`，`sig list[list[int]]`），GPU 評估器是 DStep 格子步驟序列。GPU 快 44～105× 的算力目前完全進不了樹的「審查→改進」迴圈，N3 GP 也只服務 DStep 空間。
證據：`ws/hammer/ops.jsonl` 的 comb payload；`native/gpu/space.hpp` 的 DStep；`reports/native-cuda-1109/prototype.md`「與 seed AST 空樹語言不同」。

**R2 改進迴圈的唯一非 LLM 來源（睡眠造詞）很快就乾涸。** 8 個 epoch 之後 lib_size=3、`stall=stop`、AUC_L 40 < 手寫 48、H8 恆為 0。造詞只能從已解的程式抽片段，可是已解的題太少，形成雞生蛋的問題；`near_top`（接近解但沒中）這類資訊沒有被拿來當改進材料。
證據：`ws/hammer/epochs/8/curve.csv`、`epochs/8/solutions.jsonl`、r09 `04-總結簡報.md` M2(d)。

**R3 審查與改進只有「重型」一檔，沒有便宜的階梯。** ops 列已經帶有 `evidence{new_solves, shadow_epochs, witness_hits}`、`ttl`、`tried_env_hashes`，但沒有逐節點的固定審查程式（例如近 N 次成功率），也沒有便宜的改進器（例如參數暴力搜尋、特定替換）。gate 的參數「多半沒作用」，卻沒有機制發現並淘汰它；`witness_hits` 恆為 0，layer-2 掃描在活樹上是 0 筆，`evals_meta=0`。
證據：`ws/hammer/ops.jsonl` 的 gate_g1 列；`epochs/8/curve.csv` 的 evals_meta；r09 `05-白話進度.md`。
