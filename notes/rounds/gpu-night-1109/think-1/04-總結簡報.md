# think-1 總結簡報：給 aos 樹裝上體重計

← [本輪進度](progress.md)｜[代定清單](代定清單.md)｜[夜跑看板](../README.md)

## 一句話結論

這輪沒有多解任何一題，也本來就不是要多解題。這輪做的是給活樹（hammer，跑了 8 輪的那棵 aos 樹）裝上兩把尺：一張「每個積木在不在幹活」的計分卡，和一條「整棵樹有沒有越搜越快」的曲線尺。兩把尺今晚都實跑過，算出的數字跟事先手算的期望值完全一樣。

下一步要做的是第三把尺「雜訊尺」，用來分辨改進是真的變好還是運氣好。另外有一件事要你看：你說的「整棵樹拿去做遺傳搜尋」，跟這輪設計的粒度不一樣。

## 這輪反省出什麼

**活樹卡住了，原因不在積木太少，而在改進迴圈本身。** 8 輪之後，樹的積木庫只有 3 個積木，然後自己停下來（stall=stop）。它的學習曲線分數是 40，還輸給手寫版的 48。

反省出六個斷點，白話講就是：

- **兩套語言，接不起來。** GPU 那台每秒能試上億支程式的機器講「格子步驟」語言，活樹講「清單運算」語言。GPU 算得再快，也進不了樹的改進迴圈。
- **不靠 LLM 的造積木管道很快就乾了。** 樹只能從已經解出來的題裡抽片段來造新積木，可是解出來的題太少，變成雞生蛋、蛋生雞。那些「差一點就解出來」的題目也沒有被拿來利用。
- **只有大手術，沒有小診所。** 想檢查一個積木有沒有用，得整棵樹重跑 5 分鐘。樹裡有 7 個參數型節點，它們的證據欄位全是 0，也就是說從來沒人量過它們有沒有作用。
- **靠 LLM 寫蠟模（先讓 LLM 猜解題步驟，再一步步擬合）的產出率很低。** 257 份蠟模裡只有 4 份能一路擬合到底。
- **一輪太慢。** 8 個 epoch 要跑 5 分鐘，「改一處、量一次」的機會太少。
- **改進過程本身沒有尺。** 沒有辦法自動比較「改之前」和「改之後」，所以元優化（優化「優化流程」本身）無從下手。

## 施工做了什麼（塊 A：兩把尺）

今晚只動第一塊。兩支腳本都只讀樹的檔案、不改樹，各跑 0.02 秒。實跑前後樹的指紋（sha1）完全相同，樹的自我檢查也是 0 錯。

**計分卡（`scripts/think1_audit.py`）像是給每個積木做一次健康檢查。** 樹裡 21 個積木各得到一列，記錄它在幾題的解裡被用到、最近幾輪有沒有出力、閒了幾輪，最後貼上一張標籤。結果是：4 個在幹活（keep），5 個休眠很久、該考慮清掉（dormant-stale），5 個休眠但還有動靜（dormant-active），7 個從來沒被量過（unmeasured，就是上面說的那 7 個參數節點）。

**曲線尺（`scripts/think1_meter.py`）像是整棵樹的體重計加帳本。** 它把 8 輪的成績加總成一個數，也照你「判準是搜得更快，不是解題數」的方向，另外加了一個「速度分數」：每一輪比空庫的時候省了多少搜尋量，全部加起來。現值如下：學習曲線 40、速度分數 43.5、總算力約 2.2 億次評估、LLM 呼叫 0 次。它也能拿兩次結果直接相減來比較，但因為還沒有雜訊尺，比較結果目前只會標「不知道顯不顯著」。

## 要你看的四件事（其餘是照原則推得出來的代定）

這四件都已經先照預設往下做了，你改選的話照「翻案」那句改就好。

**1. 遺傳搜尋的「個體」是一支程式，還是一整棵樹？（跟你的方向有衝突）**
你說要把整棵 aos 樹轉成 json／janet 之類的文字，再拿去突變、交配。可是這輪的設計（fable 稿）只打算把「單支積木程式」編碼給 GPU 做遺傳搜尋，粒度比你說的小一層。目前的預設是：先做「把 GPU 找到的解翻譯成樹的語言」這座橋，整棵樹的演化排到思考輪 2。
翻案：如果你要的是「整棵樹當個體」，語言橋的編碼那段改成以整棵節點樹（節點表＋參數）為單位，單支程式的編碼降為次要。

**2. 神經排序器什麼時候開始訓練？（輕微衝突）**
預設等到累積 200 支以上「訓練題全對」的程式再訓練，因為現在的正例太少，GPU 也正被長跑佔用。這段期間只做不用神經網路的統計先驗。另外，「題目特性」的資料現在就在收（N4 那條線），只是先不拿來訓練。
翻案：要現在就訓練的話，可以先用 GPU 格子步驟的解，訓練一張「哪一步接哪一步的機率表」，但只能服務格子步驟那套語言。

**3. 雜訊尺怎麼量？（原則推不出答案，統計方法的取捨）**
樹是純 CPU 枚舉，同一個設定跑兩次結果多半完全一樣。所以預設是：同設定跑兩次只用來確認「確實可重現」，波動大小改成「把題目重新抽樣 1000 次」來估。
翻案：如果你想要的是「換亂數種子、換預算」造成的波動，快撥樹要多跑 5 次以上（約 4～5 分鐘），再多一欄記錄。

**4. 不靠 LLM 造積木，要用哪種方法？（原則推不出答案，演算法選擇）**
原稿是拿「差一點就解出來」的程式，挖掉一塊再補一塊，看格子相符率有沒有變高。Argon 審稿指出這樣會被騙：把整張圖塗成背景色，相符率就能漲 30% 以上，可是語意完全錯。預設改成：在兩題以上的已解程式裡找共同的骨架抽出來當積木（Stitch 式），並以「省下多少描述長度」當門檻，不看像素相符率。
翻案：如果你偏好挖洞補洞，至少要改用更嚴格的比對方式，拒收只輸出常數的子樹，工期也要估得更長。

## 下一輪該反省什麼

**第一優先：先把雜訊尺做出來（塊 B）。** 沒有雜訊尺，任何「改了之後變好」都可能只是運氣。做法是複製一棵縮小預算的「快撥樹」，讓一次量測從 5 分鐘降到 1 分鐘以內，再量出波動大小。往後的改進只有超過兩倍波動才算數。

**第二：Argon 的兩條高嚴重警告，要在設計時就擋掉。**
- 不能偷看考卷：驗證池的題目一旦拿來造積木，再用同一批題目考它，分數就是灌水。這條已經定成規矩，下一輪施工時要寫進程式裡守住。
- 格子相符率會被「塗背景色」騙。往後任何拿相符率當門檻的地方，都要改用描述長度，或者先把顏色換算掉再比對。

**第三：語言橋到底要接到哪一層。** 這就是上面第 1 件事。是「把 GPU 的解翻成單支程式」，還是「整棵樹序列化成 Janet 再演化」，決定了下一輪要蓋哪座橋。

<details><summary>建議 3、4、8 為什麼要一起想</summary>

這三條講的是同一件事的三個面向：積木可以有大有小（8），大積木裡面包著小積木（3），改進的時候從大積木往小積木一層層分派責任（4）。它們需要同一套東西：一種能表示「樹裡有樹」的格式（也就是建議 1 的序列化），加上一本能把功勞和成本分給每一層的帳（建議 5、6）。所以思考輪 2 最好把 1、3、4、5、6、8 當作一個主題來設計，第一步就是 aos 回信建議的「樹 ⇄ JSON 來回轉換、共用子樹只記引用」。
