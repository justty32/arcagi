# 02b Argon 審（Gemini 4 Argon (High)，agy headless，全文貼提示、不用工具）

← [02-規劃-fable](02-規劃-fable.md)｜[代定清單](代定清單.md)

## (A) 審查

1. **[高] R1 訓練料極度匱乏（7/100 題）與統計先驗維度爆炸（推論與量法漏洞）**
   - **問題**：規劃稿坦承 `seed` 在 1e6 僅解 7/100 題，卻在 R1 設計學習 `P(原語 | 回傳型別桶, 深度)` 與 `P(子項型別桶 | 原語)`，並做 leave-one-task-out（加一平滑），以「7 題到解節點數中位 ≤0.5×」為繼續門檻。30 個原語 × 多個型別桶 × 6 層深度動輒數百個參數桶，但 7 棵解樹總計不到百餘個 AST 節點；加一平滑後幾乎全退化為均勻分布。更嚴重的是**倖存者偏差**：這 7 題本就是無先驗時最淺的題，若某題獨用某原語，leave-one-out 反而會將該原語降權導致變慢；且樣本數 $N=7$ 的中位數（第 4 題）統計波動極大，不具決策信度。
   - **修正建議**：(1) **降維**：拔除「深度」條件，改學與深度無關的 `P(原語 | 回傳型別, 輸入輸出形狀關係)` 與父子二元轉移 `P(子原語 | 父原語)`；(2) **擴充訓練源**：納入分解子題命中、高近似分（通過部分 train pair）子樹，或由合成題產生先驗；(3) 分母擴至 1e7 已解集（含 evaluation 對照）再算中位數。

2. **[高] R1「按先驅分攤每層預算（延後不丟）」與由下而上 Bank 搜尋的跨層相依矛盾（推論漏洞）**
   - **問題**：Q3 與 R1 宣稱「每層按先驅排 job 順序並分攤節點預算，低先驅延到下一輪補齊，不丟候選」，並推算每層 $b \to 0.8b$ 六層可省 $1/0.8^6 \approx 3.8\times$ 且保證 `0 mismatch`。這是對 bottom-up 觀測等價搜尋的機制誤解：
     - 若跑完第 $d$ 層全部候選才進第 $d+1$ 層，則第 $1 \dots d-1$ 層節點數 100% 跑滿（$b \to 1.0b$），只有最後命中層因排序早停，總節點最多省 30%～50%，**絕無跨層指數複利**。
     - 若第 $d$ 層只跑 80% 就進第 $d+1$ 層，所有依賴那 20% 低先驅子項的高層高先驅程式在當輪**根本無法生成**；而事後回頭補齊第 $d$ 層時，若無 Semi-Naive（增量笛卡兒積）引擎，不是漏解（違反 `0 mismatch`）就是整棵樹重跑。
   - **修正建議**：廢棄含糊的「層內延後補齊」，直接改為**「整數代價分桶（Cost-Bucketed DP / Levin Search）」**（見提案 4），以代價總和取代深度分層，天然兼具跨層指數壓縮與 100% 完備性。

3. **[高] L1 誤以為 `map`/`zipwith` 的一階 body 是「Bank 現成函式 entry 可直接查表」（事實與架構錯）**
   - **問題**：規劃稿在「四方向比較」說 lambda 需在 kernel 內解釋，卻在 L1 改口稱「body 就是 bank 中函式型 entry，kernel 內查表求值，不開 `native/gpu/ast/`」。在觀測等價 bank 中，entry 存的是「在各 train 頂層輸入上的具體輸出值」。但 `map(f, xs)` 的 `f` 作用於 `xs` 拆開後的**每個內部元素**（對不同 `xs`、不同位置皆不同）。除非元素型別是極小定義域（如 $0\dots 9$ 色碼）可建 10-entry LUT，否則對 `list<int>`（如網格的每一列）根本不可能在 bank 預存通用查表！
   - **修正建議**：將 L1 的 `map/zipwith` 拆成兩類處理：(1) **Point-free / 單一原語或一階柯里化 body**（如 `map(reverse, xs)`、`map(add(c), xs)`）：不查表也不寫 AST 直譯器，直接將外層 list 攤平為 Batch 維度，重用現有 20 個一階 GPU kernel（見提案 1）；(2) **小定義域純量函式**：才用預建 LUT 查表。

4. **[中] M0 與 Q5 的 Amdahl 門檻漏算「原語內含的 Host 簿記」與「單次 Launch 批量過小」（量法與門檻問題）**
   - **問題**：Q5 設定 L1 開工門檻為「`map+zipwith+if` 占 Enumerator 時間 ≥50% 且 host 簿記 ≤25%」。但 N5b 已證明：當單層候選數過小時，GPU 僅 0.13×～2.6×。在 `seed` 中，`map/zipwith` 若按型別與子項桶拆成大量細碎的搜尋任務，即便總時間佔 50%，搬上 GPU 也會因每次 launch 僅數百～數千個候選而重演 N5c（0.43× 負加速）。此外，原語耗時統計極易把該原語的「配對枚舉＋型別檢查＋bank 插入」算進 `map` 頭上，高估可搬上 GPU 的純求值比例 $f$。
   - **修正建議**：M0 的 `--seed-prof` 六桶表必須將每個原語拆為 `host_gen_dedup_ms` 與 `pure_eval_ms`，並增列**「單次可合併求值的平均候選批量（batch size）」**。Q5 門檻需加上：`pure_eval_ms ≥ 50%` 且單次 launch 中位批量 `≥ 50,000`。

5. **[中] B1 將 `--gpu-min 200000` 在 1e6 的「純 CPU 退化」誤判為 GPU 持平（事實與基準錯）**
   - **問題**：規劃稿稱「100 題 1e6 中 `--gpu-min 200000` 今天已持平 9.1 s」，並將其列為 B1 失敗的凍結備案。但依 N5b 數據，第 5 層候選遠低於 20 萬，第 6 層直接跳至 1.37M（已破 1e6 總預算）。因此在 1e6 預算下設 `--gpu-min 200000`，實質上是**「99% 以上的層完全不進 GPU、退化回純 CPU 執行」**，當然與 CPU 持平！用 1e6 作為 B1 的持平驗收無法測出常駐顯存對中大層的真實效益。
   - **修正建議**：將 `--gpu-min` 調降至 `10,000～20,000` 來驗收 B1 的 1e6 表現（要求 wall ≤ 純 CPU），並以 **1e7 預算**作為 B1 的主驗收基準。

6. **[中] T1 題目路由器的跨引擎錯位，以及對「起點樹不含 ARC 知識」的雙重標準（推論漏洞）**
   - **問題**：規劃稿在 Q2 拒絕用 N4 特徵助 `seed` 排序，卻在 T1 用 N4（N2 手寫格子原語的近似分數斜率 `best_d1..d6`）去分配秒數。
     - 若 T1 分配的是 **N2 的秒數**，則只衝高 N2 解題數，對本輪核心判準「`seed`（aos 樹）搜樹速度」貢獻為 0。
     - 若 T1 分配的是 **`seed` 的秒數**，N2 的 `gravity/fill_enclosed` 近似分數斜率與 `seed` 的通用 `list/int` 樹空間毫無幾何對應，會把預算錯配給「N2 容易接近、但 `seed` 組不出來」的題目。
   - **修正建議**：砍掉 T1 跨引擎路由器；改在 R1 納入**「100% 通用的輸入輸出資訊論/形狀特徵」**（如輸入輸出維度差、長度比、值域子集關係），這對任何符號任務皆成立，完全不違反「起點樹不含 ARC 專屬知識」。

7. **[中] 資源調度衝突：主線 M0＋R1 全程閒置 GPU，違背「能用 GPU 就用」原則（規劃漏洞）**
   - **問題**：使用者明確偏好「能用 GPU 就用、不用降低負載」，但規劃稿排出的主線（M0 跑 CPU 剖析、R1 跑 CPU 統計與排序、T1 跑 CPU 腳本），除 B1 小修外，幾乎讓 RTX 5060 Ti 在主線開發期間完全對 `seed` 搜樹袖手旁觀。
   - **修正建議**：將 CPU 開發（M0/R1）與 GPU 算力線解耦並行——GPU 除執行 B1 外，立即投入「GPU 批量展開 `map/zipwith`（提案 1）」或「GPU 逆向合成先驗訓練集（提案 2）」。

8. **[低] 過度外推 N5 教訓，混淆「等價類內冗餘」與「無效唯一值爆炸」（推論漏洞）**
   - **問題**：規劃稿多次以 N5（語法樣式剪枝僅擋 0.5–3%）為由，斷言「硬剪枝無收益」。但 N5 擋的 `reverse(reverse(x))` 與 `x` 觀測值完全相同，本來就會被 bank 的 64-bit 指紋去重 100% 吸收；而真正拖慢搜樹的是**「產生全新 64-bit 指紋、塞進 bank 參與後續層指數笛卡兒積」的無用唯一值**。
   - **修正建議**：M0 與 R1 的核心評估指標除 `eval_steps` 外，必須增列**「到解時的 Bank 唯一值總數（Bank Size at Solution）」**，並針對「進入 Bank 的唯一值」做資訊退化過濾（見提案 5）。

## (B) 提案

1. **將 `map` / `zipwith` 轉為「多維度批次（Flattened Batch）」直接重用現有 20 個一階 GPU Kernel**
   - **為什麼回報更高**：繞過「在 GPU 寫 AST 直譯器」的高工時陷阱。在 `seed` 裡，大量 `map(f, xs)` 與 `zipwith(f, xs, ys)` 的 `f` 其實是單一內建一階原語（Point-free，如 `map(reverse, grid)`）或一階原語的常數柯里化（如 `map(add(c), xs)`）。對 GPU 而言，對「$M$ 個 train 範例的 1D list」做一階運算，與對「$M$ 個 2D grid 攤平後的 $\sum H_i$ 條列向量」做一階運算，**完全是同一個 Kernel，只需把 Batch 維度放大 $H$ 倍**！這不僅免寫 AST 直譯器就能直接吃下 `map/zipwith` 的大頭、突破 1.35× Amdahl 牆，更因為展開後元素數量暴增 $10\sim 30\times$，順便餵飽 GPU，一舉消除 N5b 的「小層啟動開銷」！
   - **成本**：小～中（1–2 個工作段；只改 `native/gpu/seed/` 的 batch 索引映射與 `seed_enum_gpu.cpp` 派發）。
   - **第一步**：在 M0 剖析時統計 `map/zipwith` 中「body 為深度 1（單一原語或常數偏應用）」的時間與節點佔比；並在 `native/gpu/seed/` 新增 `ragged_flatten` / `unflatten` 輔助層，讓既有 20 個一階 kernel 直接支援 `list<list<T>>` 的內層批次求值與 64-bit 指紋歸約。

2. **雙向搜樹（Bidirectional Meet-in-the-Middle）：GPU 常駐「逆向目標光暈（Target Halo）」**
   - **為什麼回報更高**：規劃稿追求 $b \to 0.8b$（六層省 $3.8\times$），但雙向搜尋能直接把搜尋深度從 $D$ 砍到 $D-1$ 或 $D-2$（在每層膨脹 $15\sim 30\times$ 的樹上，等於 **$15\times \sim 400\times$ 的真實加速**）。`seed` 的一階原語中，許多具有確定逆運算或強結構逆條件（例如：若頂層為 `reverse(z) == Y`，則必有 $z == \text{reverse}(Y)$；若為 `transpose(z) == Y`，則 $z == \text{transpose}(Y)$；若為 `repeat(z, k) == Y`，則 $Y$ 必須具備週期 $k$，否則整條分支不可能成立；若為 `concat(a, b) == Y`，則 $a, b$ 必為 $Y$ 的前後綴切分）。從目標輸出 $Y$ 逆推 1～2 層，僅會產生數十至數百個「逆向子目標指紋（Target Halo）」。將這張小表常駐於 GPU Constant/Shared Memory，正向搜到第 $D-2$ 層時，GPU kernel 產出 64-bit 指紋的瞬間即可 $\mathcal{O}(1)$ 查表命中，直接省去最龐大的最後 1～2 層展開！100% 通用，零 ARC 專屬知識。
   - **成本**：小（1 個工作段；約 150 行 C++/CUDA）。
   - **第一步**：在 `seed_enum.cpp` 開搜前，對當前題目的目標輸出 $Y$ 套用可逆一階原語（`reverse`、`transpose`、`add/sub` 小常數、`repeat` 週期拆解），算出深度 1～2 的逆向目標 64-bit 指紋集（並標記對應的逆向結尾原語），上傳至 GPU 供每層去重時同步比對。

3. **GPU 自對弈逆向合成（Wake-Sleep Hindsight Sampling）—— 1 小時量產百萬筆通用排序器訓練料**
   - **為什麼回報更高**：徹底解決 R1「1e6 只解 7 題、無訓練料可學」的死結，同時把閒置 GPU 用在刀口上。既然 N5b 的 GPU 已經能高速展開 `seed` 並做 64-bit 觀測等價去重，任何一個進入 Bank 的唯一值 $V$（只要在各 train pair 上非退化、非全常數），其對應的生成樹 $P^*$ **根據定義就是從輸入 $X$ 產生輸出 $V$ 的最短（最小深度）通用程式**！將 $(X, V) \to P^*$ 直接收錄為訓練樣本（Hindsight Experience Replay），不需解出真題，跑完 100 題的深度 5 Bank 就能免費收穫 $10^5 \sim 10^6$ 筆「給定輸入與目標輸出特徵 $\to$ 最優通用 AST 原語序列」的完美訓練料，足以訓練高精度的條件先驗表甚至極輕量級 GPU 價值排序器。
   - **成本**：小（1 個工作段寫 Bank 逆向傾印與特徵萃取腳本）。
   - **第一步**：擴充 `seed_record.py` / `arcbatch`，在跑完深度 4～5 的 Bank 後，隨機抽樣 50,000 個非退化（跨例不同值且非恆等）的 Bank 唯一 entry，傾印其 `(輸入形狀/值域特徵, 該 entry 輸出形狀/值域特徵, 生成該 entry 的頂層與次層原語)`，直接餵給 R1 訓練條件先驗。

4. **以「Levin 整數代價分桶（Cost-Bucketed DP）＋通用 I/O 不變量條件化」取代 R1 的層內分攤**
   - **為什麼回報更高**：直接修復 R1 的架構缺陷，且**不需任何訓練料就能在第一天生效**。先根據每題輸入 $X$ 與目標 $Y$ 的純通用數學不變量 $\mathcal{I}$（如：維度是否相同 $\text{rank}(X)==\text{rank}(Y)$、長度是否守恆 $\text{len}(X)==\text{len}(Y)$、長度是否整除、值域是否為子集 $\text{set}(Y) \subseteq \text{set}(X)$），動態給每個原語賦予整數代價 $w(\text{op} \mid \mathcal{I}) \in \{1, 2, 3, 4\}$（例如當輸入輸出長度相同時，保長原語 `reverse/map/zipwith` 代價為 1，變長原語 `concat/repeat` 代價升為 3）。程式總代價為 $C(f(g, h)) = w(f) + C(g) + C(h)$，引擎改按代價桶 $C = 1, 2, 3 \dots$ 由小到大枚舉。這不僅具備嚴格的跨層指數加速（把不吻合不變量的組合推遲數個數量級），而且每個代價桶內部完全獨立，可整桶打包成單一巨型 GPU launch！
   - **成本**：小（1 個工作段，修改 `seed_enum.cpp` 的分層迴圈由 `depth` 改為 `cost_bucket`）。
   - **第一步**：定義 4 條零樣本通用 I/O 形狀/值域不變量規則，將原語代價定為 $\{2, 3, 5\}$，把 `seed_enum.cpp` 改為按代價桶枚舉，在 M0 基準上實測到解節點數與 Bank 大小降幅。

5. **GPU 指紋端「跨例資訊坍塌過濾（Information Collision Tagging）」—— 壓制垃圾唯一值進 Bank**
   - **為什麼回報更高**：N5 證明擋「等價重複值」無效，因為 Bank 去重已涵蓋；但 Bank 擋不住**「指紋全新、卻已喪失區分力」的死路唯一值**。在確定性純函式搜尋中，若兩個 train pair 的目標輸出不同（$Y_i \neq Y_j$），但某個候選子程式在兩例上算出的中間值卻完全相同（$V(X_i) == V(X_j)$，發生資訊坍塌），則任何僅依賴 $V$ 的一元後繼鏈 $g(h(V))$ 在兩例上也必然永遠相等，**絕對不可能生出 $Y_i \neq Y_j$**！在 GPU 算 64-bit 指紋時順手標記這類「資訊坍塌（Collision）節點」，禁止它們單獨作為後續一元原語（或不含原始輸入之二元原語）的子項，可在不失任何真解（`0 mismatch`）的前提下，將每層有效分支數 $b$ 實質砍低 15%～40%，產生真正的跨層指數複利。
   - **成本**：小（半個工作段；在 GPU 指紋計算與 `seed_enum` 候選配對加入 1-bit `collapsed` 標記）。
   - **第一步**：在 M0 基線剖析中，量測 Bank 內唯一值有多少比例發生「$V(X_i) == V(X_j)$ 但 $Y_i \neq Y_j$」的跨例坍塌；隨後在 `seed_enum` 加入規則：一元原語拒絕接收 `collapsed` 節點，二元原語至少需有一側為 `non-collapsed` 節點。
