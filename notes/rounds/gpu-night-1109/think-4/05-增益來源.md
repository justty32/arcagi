ELI5：我們以為把「造新積木」關掉，樹就不會學了。其實它還有第二個學習管道：記下第一輪答案用了哪些積木，下一輪先試那些。這個管道沒關，所以「不學」的樹還在學。

## 結論

**不是量尺 bug，是 no-learn 配方漏關一條學習管道：primitive 使用次數 → 列舉先後順序（DreamCoder 式先驗重排）。**

- hammer `epoch.py:317-321`：每輪把過 gate 的程式拆出運算子，累加到 `live/state.json` 的 `uses`。這段在 `learn = not frozen_engine`、`_paused(grow/foundry/judge)` **之前**，任何暫停都擋不到。
- `epoch.py:250`（`_main_run`）：下一輪 `order = compress.order_from_uses(uses)`（`log1p(uses)`）傳給 arcbatch 當列舉先驗。
- e0 時 `uses={}` → order=None；e1 起有序 → 同一程式更早被列到。e1 之後排名幾乎不變 → e1..e4 平（每題的一步增益被乘 E=4）。
- 排除其他候選：**隨機種子**——無（native 決定論，親代兩次 run 每題 b 全等）；**快取**——各 run 目錄獨立、`ops.jsonl` 9 行前後不變、lib_size 恆 0；**預算重分配**——evals_body 只差 3%，且題目是 ntf 變小非預算變大；**judge 重排**——promoted=0、n_incubating=0；**meter 算法**——`verify` 由原始 solutions.jsonl 重算全 PASS，下表與 meter.json 一致。

## 對判定的含意

- 親代 gain 173.3 ＝ 順序先驗 ≈85 ＋ comb 積木 ≈88。舊 no-learn 只剝掉後者，所以 Δ≈−88 是「comb 管道」的貢獻，不是「全部學習」。
- 為何 z 小：親代多了 comb 後 lib 變大，純 primitive 程式的列舉被稀釋 → 11 題 no-learn 反小勝（0.2–1.7 bit，6150a2bd 14.7），4 題 comb 大勝（−21~−33）。這是真實取捨不是雜訊，但讓 pstdev 很大。成對符號檢定在舊對照上也會是 4 負 11 正——**換檢定救不了舊對照**，要換對照。
- 修法（不改 hammer）：新配方 `no-learn-all` ＝ no-learn ＋ meter 每輪結束把 `live/state.json` 的 `uses` 清空（樹副本 `_metainfo.json` 加 `meter_freeze_uses: true` 標記觸發，sha 必異）。預期 e1..e4 與 e0 逐題相同、gain=0。新判準見 03「第三棒預先登記」。
