# think-2 簡報：aos 樹本身也是積木（給 fable 的自足料）

← [蒐集原稿 01a](01a-蒐集-sol.md)｜[代定清單](代定清單.md)｜上一輪 [think-1 總結](../think-1/04-總結簡報.md)

## 0. 一句話

思考輪 1 給活樹裝了「計分卡」和「曲線尺」。這輪要讓**整棵 aos 樹變成可序列化、可突變交配、可分層歸責的積木**，並把上輪 Argon 的兩條警告寫成守門程式。目標是推進 aos 體系，不追解題數；判準是「樹搜得更快」。

## 1. 使用者方向（11-09 夜建議原意，濃縮）

1. 遺傳搜尋的個體是**整棵 aos 樹**：樹先序列化成 json／janet／lua／python，再在上面突變、交配、選擇。
2. 判準是樹搜得更快／解得更快，不是解題數；GPU 長跑順帶收「題目特性」。
3. 樹可嵌套：A-B-C 可以是 D-E-F 裡的節點 D；配合節點池與分錢。
4. （修正 3）主模式是**分層式改進**：上層把改進責任（梯度）分給節點，分到責任的 D 改進自己＝對內部子樹跑一輪審查／改進（遞迴）。
5. 成本兩種付法：花時間（暴力／符號回歸）或花 token（agent）；同一本帳，依性價比挑。
6. 成本是**任意 JSON**：agent 可自創成本項、細化或統括，計算時可只取部分 key；成本結構本身也可被改進。
7. 演化中間產物不進 git，沉澱下來的才 commit；程式碼演化的基因表示想用 **Janet**（程式即資料）。往返一致判準、共用子樹改前要不要複製、自動淘汰與否→交 fable 定並附意見。
8. 樹是積木，節點也是積木；同一套入庫、計價、分錢、演化規則。節點池＝積木池。

上輪留下的衝突 Q1：think-1 的語言橋只編碼「單支程式」，粒度比 1 小一層；預設整棵樹演化排本輪。

## 2. 活樹 hammer 長什麼樣（實查，路徑 `/home/lorkhan/code/playground-arc1/ws/hammer/`）

- 共 97 檔、852K；**沒有 symlink、沒有二進位、沒有 `.py` 葉子**。只有 `ctl`、`_view.sh` 兩支 755 腳本。
- **定義部分**（基因體候選）：
  - `_metainfo.json`：`born,entry("arcagi.hammer.epoch:run_epoch"),kind("tree"),name,reads,status,weight,writes`。
  - `frozen.json`：預算、`layers_max`、`taskset`（題組路徑＋SHA1）、`holdout`（H8／H24）、`purity`、`judge` 等設定。
  - `ops.jsonl`：21 列算子（kind ∈ gate／route／comb／decomp…），每列欄位 `id,kind,status,by,born,evidence{new_solves,shadow_epochs,witness_hits},payload{params…},mdl_bits,blamed_by,parent_route,env_hash,sig,ttl,tried_env_hashes`。注意 **定義（payload）與執行期狀態（evidence、blamed_by、ttl）混在同一列**。
  - `ops/<id>/_metainfo.json`：14 個子夾，只替 comb／decomp 建的投影（`ops.jsonl` 的子集，非獨立真值）。
  - `nodes/{solve,gate,grow,stall,route,judge,foundry}/_metainfo.json`：7 種節點定義，入口是 Python `module:function`；各有執行期 `_witness.jsonl`、`inbox/`、`outbox/`。
- **執行期部分**（不進基因體）：`epochs/0..8/`（每輪 `curve.csv` 單列、`solutions.jsonl`、`blocks.json`、`status.json`）、`live/`、`ledger.jsonl`、`foundry/`（LLM 請求與中間檔）、`tmp/`、`RUN`（時間戳旗標）、`think1/`（上輪尺的輸出）。
- `truth/`：初始化時釘住的題號分池（L16 訓練、P 練習、H8／H24 保留），屬設定。
- 寫入慣例（`src/arcagi/hammer/formats.py`）：JSON `indent=1, sort_keys=True`＋末尾換行；JSONL 排序 key、無縮排；原子寫（暫存→fsync→replace）。
- 成本欄目前是寫死的：`evals_body,evals_shadow,evals_meta,evals_foundry,llm_calls,wall_s,logcost_L,lib_bits`；ledger 另有 `evals.llm_tax`。
- 歸責欄現有 `blamed_by`（op）與 ablate 帳的 `blamed`；hammer **沒有**梯度信箱。

arcagi 另有 `aos/`（blocks、pool、seedlib…）：`src/arcagi/blocks/catalog.py` 支援 `$ref`＋JSON Pointer，但目前資料樹**沒有任何實際 `$ref` 或 symlink**——共用子樹今天還不存在，要靠這輪設計造出來。pool 帳本（`src/arcagi/blocks/pool/ledger.py`）已實作：每解一題 1000、頂層留 20%、餘按靜態引用分、房租 100、連三輪零分紅列建議退休；梯度信由 near-miss 依 `pixel_acc` 排序寫 `_gradients.jsonl`，但分紅**沒讀回**這些信。

## 3. aos 那邊的工具與規則（唯讀參考）

- **沒有任何現成工具**能把一棵 aos 樹轉成 JSON／Janet 再轉回來。`aos-lua`、`aos-janet` 只有語言→資料夾；`aos-grow` 只搬單格；`aos-json ref --move` 只拆不併，`check` 可當變異後的形狀過濾器。
- C-51（10-15）資料夾⇄JSON 對應：資料夾＝object、key 保留副檔名、非 JSON 檔用存根 `{"$file":…}`、隱藏檔略過、執行期檔（state／ctl／lock）不攤開；**只當工具與思考方式，不寫進規範**。
- 往返會掉資訊的點：權限位、symlink（要記成引用不抄內容）、非 JSON 葉子、執行期檔、搬位置會改行為（相對 `$ref`、cwd）、排版與 key 順序（要先講好比位元組還是比內容）。
- aos 建議的第一步：在一棵小樹上做「樹⇄單份 JSON」雙向轉換，共用子樹記引用不展開；驗收＝轉出再轉回內容相同、跑出來結果相同。過了才接變異（改 JSON 值）、交配（換子樹，只收過 `check` 的）、適應度用 pool 帳本。Janet／Lua／Python 只是同一份 JSON 的另一種寫法，JSON 通了再說。
- Janet：本機有 `/home/lorkhan/.local/bin/janet`；`~/repo/langs/janet-lab` 用 `spork/json` 做 JSON⇄Janet；注意 JSON null 與 key 次序在 Janet 往返會有差。aos-janet 的寫法如 `(def program (dir "_entry" (inst ["echo" "hi"])))`。
- 節點池定稿（aos 11-08，`/home/lorkhan/repo/simple_tools/aos/proto8/thinking/2026-11/08/node-pool/README.md`）：錢＝千 token＋秒/10；頂層收「任務數×價」；每層先報銷自己實耗、利潤留 20%、80% 按靜態引用分；梯度信 score −1～1 換成 0.5～1.5 倍乘數；退休要人按、可復活；複製只在「兩個上級連續 2 epoch 給相反分數」時由上級出錢。實測教訓：錢對學習曲線影響≈0、最貴節點先餓死、零花費腳本永不退、每輪都叫同批節點→退休訊號量不到。

## 4. 上輪遺留（塊 B 與 Argon 警告）

- 塊 B 原提案：複製空起點樹（排除 epochs／live／tmp／ledger），L=25000／P0=10000／4 epochs、目標 ≤40 秒；Argon 改成 L 保 50k、6 epochs、靠 L16 子集縮時。雜訊：同設定兩跑只驗決定論（Δ=0），σ 用題目 bootstrap 1000 次。正式設計還沒寫，不是已完成資產。
- 上輪尺：`scripts/think1_audit.py`（計分卡，欄位 `id,kind,…,uses_L,uses_P,hit_rate_10,idle_epochs,verdict`）、`scripts/think1_meter.py`（曲線尺，`auc_L,auc_speed_L,cost,llm_calls,eff,per_epoch…`；compare 讀同目錄 `noise.json`，缺檔則 significance=null）。
- **Argon 警告一（不准偷看考卷）**：驗證池題目不得拿來造積木。**現況已違反**：`epoch._main_run` 的 gate_ids 是 L16∪P，`feed` 收所有 gate_ok 交 `sleep_ops` 造候選——P 在程式裡叫 practice，但同時被 judge 拿來當升級依據（影子快道 `new_solves`），等於自己出題自己考。H8／H24 未進這條路。
- **Argon 警告二（相符率會被塗背景色騙）**：`pixel_acc` 目前流入 near-miss 軌跡、pool 梯度信排序、taxonomy 排序；正式判解用 `train==targets`。「相符率提升 ≥0.10 即抽成 comb」只在上輪規劃稿，沒落地。守門的目標是：任何**門檻**（決定收／升級／退休）不准用格子相符率；排序或診斷可以，但要標記。

## 5. GPU 能接到哪

- `gpusearch`：一題一批，評估格子步驟序列索引區間；GP（`reports/gpu-gp-1109/`）個體是長 1～10 的步驟索引序列，pop 524288 約 0.5 GB 顯存。**兩者都沒有評估「整棵 hammer 樹變體」的介面**——樹的一個 epoch 是 CPU 枚舉，5 分鐘。
- 文獻可借：EvoGP（定長張量 `node_type/node_value/subtree_size`＋子樹交換，整族群 GPU 演化）、eggp（e-graph 共用子結構 id、避開已訪表達式、Pareto）、Stitch（跨題語料抽積木、壓縮上界剪枝）、DreamCoder（MDL 同時計庫與程式）、Semantic Backprop（沿圖逆拓撲分語意梯度、共享後繼聚合）、Brush（多目標保留）。

## 6. 要 fable 規劃的事（三條主題）

1. **樹⇄JSON／Janet 往返**：基因體邊界（定義 vs 執行期；ops.jsonl 每列要不要拆定義欄與狀態欄）、共用子樹的引用表示（今天還不存在，怎麼引入）、往返一致的判準（位元組／內容／行為）、Janet 何時接。整棵樹當遺傳搜尋個體時，突變與交配的運算子、合法性檢查、適應度從哪來（一個 epoch 5 分鐘太貴）。
2. **分層改進**：計分卡當節點健康檢查；改進責任與功勞怎麼一層層分給子樹（上層→節點→子樹，遞迴）；成本帳改成開放 JSON（任意 key、可細化／統括、只取部分 key），時間與 token 同帳。
3. **評判基準與守門**：塊 B 快撥樹＋雜訊尺落地；Argon 兩條警告寫成程式守門（P 池不准造積木、門檻不准用格子相符率）。

限制：GPU 能用就用、顯存 ≤3GB；演化中間產物不進 git；活樹既有檔不改（只能在旁新增）；施工由 codex sol 做、品質弱，所以每塊要能落成「具體檔案＋格式＋驗收條數」；第一塊建議是往返工具。
