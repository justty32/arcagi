# think-5 01 簡報：「一次 GPU 同步涵蓋多題／多層」能否讓 GPU 端到端贏 CPU

← 上輪 [think-3 代定清單](../think-3/代定清單.md)（E1–E19）｜[think-4](../think-4/progress.md)（量尺，與本輪無關）
本檔自足；數字出處括號標 commit／報告。**本輪只到 02b，不寫 03、不施工（E10 精神：GPU 架構大改等使用者）。**

## ELI5

GPU 算得快，但每問它一次要排隊。現在 seed 搜尋每「一層」就問 GPU 一次，1e6 預算下 100 題共問 6,230 次，每次等約 27 ms；而一層裡 GPU 能幫忙的 CPU 工作平均只有約 1.7 ms。所以問一次的等待比省下的還多 15 倍。兩條救法：①**跨題合批**：N 題同一層一起問一次；②**多層融合**：一次問完好幾層。另外有個大前提：今晚 GPU 被 8 個其他夜跑佔滿（100%），27 ms 很可能大半是排隊，不是 GPU 本身的延遲。

## 2. 現行 arcbatch 迴圈結構（定位）

- `native/src/batch.cpp:275`：4 條 worker 執行緒，每條自己拿題、跑完整題（題間無同步）。
- 每題 decomp 拆成多個子題（`native/src/seed_decomp.cpp`），每個子題一個 Enumerator（1e6 共 1,253 個）。
- Enumerator 由下而上逐層：`native/gpu/seed/seed_enum_gpu.cpp:767` `for (size = 2..MAX_SIZE)`，每層 `gpu_layer(size)`（:1035 起）：
  1. 總候選 `< gpu_min` → 整層走 CPU。
  2. `g_sync`（:890）上傳 bank 增量 → `e2e_begin_layer` → 依 rank 分 chunk，**walk 走到才 launch**（`e2e_run_chunk`，:1104），每 chunk 一次 D2H 同步。
  3. 段（op, comp）照原順序走：不支援段（lambda／if／block）在 CPU `apply()`；支援段讀 GPU status：NODE 批量 `++nodes`、SURV 回 CPU 走原 `emit()`（建程式、驗解、進 bank、抓與 CPU 候選的指紋雙胞）。
  4. 預算 `nodes>=budget` 隨時 `throw Done`；`nodes_to_first` 要和 CPU 逐位相同（0 mismatch 驗收）。
- **層間硬相依**：第 L+1 層的候選＝所有 ≤L 層 bank 的組合；第 L 層 bank 含 lambda／if 段（CPU）產出的 entry 與 SURV 去重結果。

## 3. 模型：同步次數 × 每次延遲 vs 工作量

設 W_g＝GPU 可做的 CPU 工作（task 秒），W_c＝其餘，s＝同步次數，λ＝每次同步延遲（含排隊），X＝kernel 對 CPU 的加速，P＝執行緒數。

  T_gpu ≈ [W_c ＋ W_g／X ＋ s·λ − overlap] ／ P，  T_cpu ≈ (W_c＋W_g)／P

打平條件（overlap＝0，X→∞）：**s·λ < W_g**。1e6：W_g≈0.26×40.2≈10.5 s，s=6,230 → **λ 須 < 1.7 ms**；量到 27 ms（≈16× 過頭）。
要拿到 ≥1.2×：s·λ ≤ W_g − (W_c＋W_g)(1−1/1.2) ≈ 10.5 − 6.7 = 3.8 s → λ·s ≤ 3.8 s。

| 情境 | s | λ | s·λ | 結論 |
|---|---|---|---|---|
| 現況 B1（汙染） | 6,230 | 27 ms | 168 s（≈gpu_s 166 s，吻合） | 0.18× |
| 現況、GPU 無他人（假設 λ≈0.1–0.5 ms，**未量**） | 6,230 | 0.1–0.5 ms | 0.6–3.1 s | 1.2×～1.3×（逼近 1.35× 天花板），**不用改架構** |
| 跨題合批 N=16（汙染 λ） | 390 | 27 ms | 10.5 s | 打平 |
| 跨題合批 N=64（汙染 λ） | 97 | 27 ms | 2.6 s | ≈1.25× |
| 多層融合（一列舉器一同步） | 1,253 | 27 ms | 34 s | 仍慢；且需 lambda 上 GPU，見 §4 |
| 合批＋融合 | ≈1,253／N | 27 ms | 小 | 天花板改由 F3 5.7×，但工程最大 |

## 4. 兩條路的理論上限與阻礙

### 4a 跨題合批（N 題同層一次 launch）
- **上限**：不改 Amdahl 分子 → 仍封頂 **1.35×**（一階支援擴到全部一階才 1.6×）。只是把 s 除 N。
- **語意**：各題 status 彼此獨立，0 mismatch 可保。
- **阻礙**：①現行是「一執行緒一題、各跑各的」，層不對齊；要改成層同步排程器（coroutine／狀態機，每 Enumerator 停在「等 GPU」點，湊滿 N 或逾時就送）。②同時活著的列舉器 ≥N 才湊得到 N；1e6 小題多數層 <gpu_min，實際可湊的大層數未知（**每層候選數分佈未量**，E14 有要求但 M0 未給）。③顯存：b1 4 context 已 549 MB 峰值，N=64 需共用池而非 per-context。④「walk 走到才 launch」改成整層預先 launch，超預算的浪費要算。
- **便宜變體（非合批，藏延遲）**：P 從 4 提到 16（本機 16 核）→ s·λ／P 降 4×；或同執行緒內預先整層 launch、先跑 lambda 段（CPU 74%）再收 status，overlap 上限≈每層 W_c≈4.8 ms，仍 < 27 ms。

### 4b 多層融合（一次 kernel 跑 L..L+k）
- **硬相依**：L+1 依賴 L 的完整 bank（含 lambda／if 段產物＋去重＋驗解＋預算截斷順序）。只在 GPU 融合一階段＝漏掉「一階套在 lambda 產物上」的組合 → 改變搜尋語意、破 0 mismatch。
- **所以融合＝整個 Enumerator 上 GPU**（含 lambda kernel L1，E5 門檻未達：46%<50%）、GPU 端去重與 rank 排序、預算截斷精確到節點。上限才換成 F3 的 5.7×（一階＋lambda 皆上 GPU、簿記留 CPU）；s 從 6,230 降到 ≤1,253（每列舉器一次）。
- N5b 的 30×（L6）就是這種「GPU 整段跑、只限一階原語」，所以不是端到端數字。

## 5. GPU 被佔滿對量測的污染

- 量測當下：`nvidia-smi` 100%、compute mode Default（時間切片），同卡 8 個行程：gpgp-overnight、gpusearch-filler／filler2／overnight、gpuprofile×2、gpgp-ho、arcbatch-gpuseed（11-10 本棒實查）。
- 時間切片下，小 launch 要等其他 context 的時間片 → λ 被灌成 ms 級；N5c 量 ≈14 ms 啟動＋等待、B1 量 ≈27 ms／層，**兩者都是污染值**。
- 汙染方向：只傷「同步次數多」的路（現況 B1、合批 N 小）；對融合／大合批傷得少。所以**汙染會系統性偏袒大改架構**，在乾淨 λ 量到前選路有風險。
- F1 的 30× 也是滿載下量的吞吐，乾淨時可能更高，但端到端被 Amdahl 封頂，不影響結論方向。
- **未知量 #1：乾淨 λ**（GPU 無他人時，一次 3 kernel＋H2D＋D2H 的往返）。量法只要一個 launch-sync 微基準，幾秒鐘，但要等夜跑停（本輪禁跑 GPU）。

## 6. 給 fable 的問題

1. 在 λ 未知下，怎麼排「先量乾淨 λ」與「合批／融合」的順序？各給停手判準。
2. 跨題合批是否值得做（上限 1.35×～1.6×），還是「提高 P＋整層預發」就夠？
3. 多層融合要不要和 L1 lambda kernel 綁成同一條路線（因為不綁就破語意）？
4. 每案的通過判準要硬數字（牆鐘比、0 mismatch、λ、s、顯存），且要防「GPU 滿載下量出假綠／假紅」。
