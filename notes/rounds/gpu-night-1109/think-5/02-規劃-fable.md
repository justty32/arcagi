# think-5 02 規劃（fable）
← [01 簡報](01-簡報.md)｜依據 F1–F7 與 §3 模型；數字另有出處者括號標。只規劃、不施工（E10）。

## ELI5 結論

兩條大改（跨題合批、多層融合）**現在都不該開工**，因為決定它們值不值得的唯一變數「乾淨 λ」還沒量。01 的模型說：單層 offload 要打平只需 λ<1.7 ms，要 1.2× 只需 λ≤0.6 ms；GPU 空閒時一次 3 kernel 往返落在 0.1–0.5 ms 是合理預期，若成立，**不改架構就能摸到 1.35× 天花板**，合批（同樣封頂 1.35×）就是白做。反之若乾淨 λ 仍 >5 ms，單層 offload 這條路死透，合批只是把死期延後（上限仍 1.35×），真正值得的只剩「整個列舉器上 GPU＋lambda kernel」（上限 1.9×～5.7×），但那是月級工程且受 E5 門檻。所以推薦：**先花半天量乾淨 λ，再花 2–3 天做「整層預發＋CPU 段重疊」這個不改架構的便宜版，在乾淨 GPU 下重跑 E8**；合批只在 λ 量出來壞、且量到「同時活著的列舉器 ≥16」才考慮。要使用者裁的是：願不願意為量測停夜跑 10–15 分鐘；E1「能用 GPU 就用」與「seed 內圈短期少吃 GPU」的衝突怎麼解；E5 50% 門檻要不要為融合路線鬆綁。

## 方案

共用記號（01 §3）：1e6 train100、P=4：W 總 40.2 task 秒，W_g≈10.5、W_c≈29.7，T_cpu≈10.1 s；s=6,230。打平 s·λ<10.5 s；1.2× 需 s·λ≤3.8 s。所有「通過」只認**乾淨條件**（見「防量測污染」），汙染下的數字只當參考。

### A　先量乾淨 λ，再做「整層預發＋CPU 段重疊」（不改架構）
- **做什麼**
  - A0 微基準：獨立小程式（放 `native/gpu/seed/` 旁，不進 arcbatch），仿 `e2e_run_chunk` 的形狀：jobs H2D → 3 kernel → status D2H → stream sync，候選數取 1e6 實況的中位（幾萬）與 p90（幾十萬）兩檔，各 1,000 次，報 median／p90／p99。同一支程式在「汙染」與「乾淨」各跑一次，差值就是排隊成本。
  - A1 整層預發：`native/gpu/seed/seed_enum_gpu.cpp` `gpu_layer()`（:997）裡 `ensure` 現在「走到才 launch 且同步」；改成 `e2e_begin_layer` 後**一次把全層 chunk 全部 launch**（gseed 後端把 `e2e_run_chunk` 拆成 `e2e_launch_chunk`／`e2e_wait_chunk`，每 chunk 一個 cudaEvent），walk 走到該 chunk 才 wait。超預算浪費：多 launch 的 chunk 只花 GPU 時間，不改 `nodes` 計數，語意不變。
  - A2 重疊：segs 迴圈中 `!g.sup` 的 CPU `apply()` 段（W_c，每層≈4.8 ms）**先於** 第一個 wait 跑完，即把 segs 走兩遍：先 CPU 段、再 GPU 段。需確認 CPU 段與 GPU 段互不讀寫同一層 bank（§2 第 3 點：SURV 回 CPU 才進 bank，CPU 段也進 bank——順序改變會影響去重勝者與 `nodes_to_first`，**這是 A 唯一的語意風險**，要以 0 mismatch 驗）。若有相依，退而只做 A1。
  - 不提 P：P 由 4 提到 16 對「比值」沒幫助——CPU 版同樣 ÷4；只有超額訂閱（P>核數）能藏等待，但 CPU 版也可開 16 執行緒，比值不變。01 §4a 的「s·λ／P 降 4×」是絕對值不是比值。
- **理論上限**：乾淨 λ=0.1–0.5 ms → s·λ=0.6–3.1 s → 1.2×～1.3×（A0 即可判）；加 A2 重疊後打平條件變 s·max(0, λ−4.8 ms)≤10.5 s，1.2× 條件變 **λ≤5.4 ms**；汙染 27 ms 下仍只 ≈0.2×，A 不是對汙染的解。天花板 1.35×（一階全支援 1.6×）。
- **工時**：A0 半天；A1 1–2 天；A2 1 天＋對帳。
- **風險**：A2 改 CPU／GPU 段順序破 0 mismatch；乾淨 λ 含 host 端 `g_sync` 增量上傳（B1 sync_s 10.1 s÷6,230≈1.6 ms／層，這段不是排隊，重疊也藏不掉，**單這項就吃掉打平餘裕的 95%**）。
- **通過判準**：
  - A0：乾淨 median λ ≤0.6 ms 且 p90 ≤1.5 ms → 直接進 A1；0.6–5.4 ms → 進 A1+A2；>5.4 ms → A 停。
  - A1/A2 完成後，乾淨條件、`--gpu-min 0`：1e6 牆鐘 ≤0.83×CPU（≥1.2×），1e7 ≥1.2×；100 題×2 預算×3 次重跑 **0 列不同**（程式、對錯、節點、nodes_to_first）；s 不增（≤6,230）；顯存峰值 ≤600 MB（B1 549）；每層 gpu_ns 中位 ≤1 ms。
- **停手判準**：A0 乾淨 λ>5.4 ms；或 A1+A2 後 1e6 乾淨仍 <1.0×CPU；或任何 mismatch 一週內修不成 bit-exact。停手後 E8 凍結維持。

### B　跨題合批排程器（N 題同層一次 launch）
- **做什麼**：`native/src/batch.cpp:275` worker 迴圈由「一執行緒一題跑到底」改成層同步排程器：每個 Enumerator 在 `gpu_layer()` 的 launch 點 yield（coroutine／狀態機），中央收集器湊滿 N 或逾時 τ 就合併一次 launch；gseed 後端改共用池（jobs／status 區段式、單一 bank 池含題 id 前綴雜湊）。B1 的 per-thread context 併為一個。
- **理論上限**：封頂仍 1.35×／1.6×（不改 Amdahl 分子）。汙染 λ=27 ms：N=16 打平、N=64 ≈1.25×；乾淨 λ 時與 A 無差。**真正前提是 N_eff**（同一時刻停在 GPU 層的列舉器數）：現行設計同時活著的列舉器 ≤P=4，要湊 N=16 必須同時開 100 題全部列舉器，host 端 bank 記憶體 ×25。
- **工時**：2–4 週（排程器 1 週、後端共用池 1 週、對帳與逾時調參 1–2 週）。
- **風險**：N_eff 不足（1e6 小題多數層 <gpu_min，E14 的每層候選分佈未量）；逾時 τ 引入牆鐘非決定性（結果仍決定性）；顯存共用池 N=64 估 1–1.5 GB；工程量與 1.35× 回報不成比例。
- **通過判準**：
  - B0 前置（唯讀量測、不改架構）：在現行程式加每層 (enumerator id, size, 候選數, 時間戳) log，離線模擬排程器 → **N_eff 中位 ≥16、p25 ≥8**，且模擬 s ≤400；否則不開工。
  - 完成後：乾淨條件 1e6／1e7 皆 ≥1.2×；**汙染條件（λ≈27 ms）1e6 ≥1.0×CPU**（這是 B 相對 A 的唯一賣點，不達就沒理由存在）；0 mismatch 同 A；s ≤400；顯存 ≤1.5 GB。
- **停手判準**：B0 N_eff 中位 <8；或 A 已在乾淨條件過 1.2×（B 失去意義）。

### C　多層融合＝整個列舉器上 GPU，綁 L1 lambda kernel
- **做什麼**：01 §4b 已證不綁 lambda 就破語意，所以 C 必然是：L1 lambda kernel（map／zipwith／if 帶一階 body，BodyPool 定長化）→ GPU 端 bank、去重（atomicMin 名次）、rank 排序、預算截斷精確到節點 → 一列舉器一次同步。檔案：新 `native/gpu/seed/` 後端 ＋ `seed_enum_gpu.cpp` 整個 `for (size=2..)` 迴圈搬進 device。
- **理論上限**：F3 1.9×（一階＋lambda 免費）～5.7×（簿記也外移）；s ≤1,253；汙染 λ 下 1e6 s·λ=34 s 仍慢，1e7 以上才有機會（W_g 隨預算長、s 長得慢；N5c 1e7 慢 1.45× 比 1e6 慢 2.3× 已顯示此趨勢）。
- **工時**：1–3 個月。
- **風險**：bit-exact 去重順序與預算截斷在 GPU 上重現；BodyPool 變長；E5 門檻 46%<50% 未達；顯存放整個 bank；與 E1「外圈優先」直接衝突。
- **通過判準**：門檻 E5 達（或使用者鬆綁至 45%）；L1 原型在 1e7 `--seed-prof` 上 lambda 段吞吐 ≥5×、100 題 0 mismatch；融合後乾淨條件 1e7 ≥1.5×、1e8 ≥2×；s ≤1,253；顯存 ≤2 GB；汙染條件 1e7 ≥1.0×。
- **停手判準**：L1 原型吞吐 <2×；或去重順序一個月內做不到 bit-exact；或使用者維持 E1=B（外圈優先）。

## 推薦路線

1. **閘 0（半天，需 10–15 分鐘乾淨 GPU）**：A0 微基準，同時跑汙染版。產物：λ_clean、λ_dirty、host 端 g_sync 每層成本三個數。這一步在夜跑全停前做不了，要使用者排窗口。
2. **閘 1**：λ_clean ≤0.6 ms → 直接在乾淨窗口重跑 E8（`--gpu-min 0`，1e6/1e7，ABAB 各 3 次）。過 → 解除凍結，到此為止，B/C 都不做（1.35× 到手，剩下的交給 E1 外圈排序器）。
3. **閘 2**：0.6<λ_clean≤5.4 ms → 做 A1+A2（2–3 天），再重跑 E8。過 → 同上；不過 → 進閘 3。
4. **閘 3**：λ_clean >5.4 ms 或閘 2 不過 → 跑 B0 量 N_eff（1 天、純 CPU 可做、不必乾淨 GPU）。N_eff 中位 ≥16 且使用者接受「封頂 1.35× 換 2–4 週」才開 B；否則 B 棄。
5. **閘 4**：C 只在使用者推翻 E1（內圈優先）且 E5 達標或鬆綁時開，且先做 L1 原型 2 週當可行性閘，不直接做融合。
6. 期間 `--gpu-seed` 預設維持 `--gpu-min 200000` 凍結（E8/E15），任何「通過」都要在乾淨條件重現一次才解凍。

## 防量測污染

- **判定乾淨的硬條件**（寫進量測腳本，不符就把報告標「汙染／僅參考」）：開跑前 60 s `nvidia-smi --query-gpu=utilization.gpu` 1 Hz 取樣全 <5%；`--query-compute-apps` 只有本行程；host `loadavg(1m)` < P；量測全程持續取樣並附在報告。
- **假紅防法**（GPU 滿載讓 GPU 版看起來更慢）：不用牆鐘單一數字下結論，改用模型對帳：量 s、每層 gpu_ns 分佈（既有 `g_prof.gpu_ns`／`chunks`）、sync_s，算 T_pred=[W_c＋W_g/X＋s·λ]/P，與實測差 >15% 就表示模型漏項，先補模型再做決定。A0 的 λ_dirty 當「汙染程度溫度計」：arcbatch 每次開跑先跑 50 層 λ canary，報告附 canary/λ_clean 比值。
- **假綠防法**（其他夜跑也吃 CPU，讓 CPU 基線變慢）：CPU 與 GPU 版 ABAB 交錯、各 ≥3 次取中位、同一窗口；CPU 基線用 task 秒加總（受排程影響小）與牆鐘雙報；兩者比值偏離 P 超過 20% 視為 CPU 被搶。
- **汙染下仍能做的事**：0 mismatch 對帳、s 與候選分佈、B0 N_eff、host 端 sync_s——都與 GPU 排隊無關，可在夜跑期間做。
- **汙染對路線選擇的系統性偏差**（01 §5）：汙染只傷 s 大的路，會偏袒 B/C。所以**任何在汙染下「B/C 看起來比 A 好」的結論一律不採**，只採乾淨條件結果。

## 方向題

1. **先量 λ 還是先動工？** 推薦：先量，為此停夜跑 10–15 分鐘。後果：不停就只能在汙染下猜，風險是為 1.35× 做 2–4 週合批。**使用者裁**（排窗口）。
2. **跨題合批值不值得？** 推薦：不值得作為獨立路線；只在閘 3 條件（λ_clean 壞 ＋ N_eff≥16）下考慮。後果：放棄「汙染 GPU 下也能贏」的能力——但夜跑共用 GPU 本來就不是 seed 的設計目標。**使用者裁**（E1 衝突：「能用 GPU 就用」vs 外圈優先）。
3. **融合是否必綁 L1 lambda kernel？** 推薦：是，否則破語意；且 L1 先做 2 週原型當閘。後果：C 變月級；E5 門檻 46%<50% 要不要鬆綁到 45%。**使用者裁**（E5）。
4. **凍結要不要維持到乾淨 E8 過？** 推薦：維持（E8/E15）。後果：期間 `--gpu-seed` 等同純 CPU，GPU 全給夜跑。不必裁，照既定。
5. **判準用 1e6 還是 1e7 當主尺？** 推薦：兩者都要過 1.2×，但解凍以 1e7 為主（實際用量；且 s/W_g 比例對大預算有利）。後果：1e6 若只打平也可解凍（當 `--gpu-min` 自動依預算調）。輕裁即可。

## 疑點

1. **乾淨 λ 的真值**：27 ms 裡有多少是排隊、多少是 host 端固定成本（g_sync 增量上傳 ≈1.6 ms／層、chunk 規劃、pinned 拷貝）。若 host 固定成本就 ≥1.7 ms，A 連打平都不可能，整條單層 offload 路線要直接結案——這是 A0 一定要把 host 段拆開計時的原因。
2. **N_eff 的量級**：現行一執行緒一題，同時活著的列舉器 ≤4；B 要改成百題同時活著，host 記憶體與 bank 重建順序是否還能維持 0 mismatch（bank 進入順序跨題無關，理論上可，但 decomp 子題間有無共享狀態我沒讀 `seed_decomp.cpp` 確認）。
3. **A2 重疊的語意安全**：CPU 段 `apply()` 與 GPU SURV `emit()` 若都往同一層 bank 寫、且去重勝者取決於誰先到，把 CPU 段提前就改了 `nodes_to_first`。01 §2 第 3 點暗示兩者都進 bank，所以 A2 可能只能部分重疊（先 launch、CPU 段照原順序、只藏 launch 不藏 wait），重疊上限會低於 4.8 ms。
