## 1. 目標與使用者前提（原話整理）

- 使用者：「就是拿我們這套 aos 體系去嘗試解 arcagi」。用**符號邏輯**解 ARC-AGI-1；LLM 只用來找規則、寫程式、蒸餾，最終解題靠確定的程式；**神經網路盡量不用**。可暴力吃 CPU、可寫 CUDA（RTX 5060 Ti 16GB）。
- 遠期：「arc agi 1 …是種子，後面會慢慢成長直到能完全代替 LLM 作爲思考驅動」「從聰明高階 LLM 蒸餾出智能種子，等到其成長到能自我吸收營養進行 RSI」。所以**能累積、能自我長大的結構**比一次性的分數更重要，但分數仍是量尺。
- **本輪新要求**（aos 轉達，11-08 11:45）：第一輪代定 D9（不用 aos 形式包裝）只當起步；**第二輪要開始把 aos 體系接進來**——例如積木／求解器做成 aos 的資料夾程式、蒸餾與積木記帳參考 aos 的 node-pool 與 kb-ideas 想法 20～22。怎麼接、接多少由你規劃決定。
- 方向問題不停線：隊長代定、記代定清單，使用者回來翻案。

## 3. 第一輪成果（已有，直接延用）

- 成績：**evaluation 21/400**、training 57/400（identity 0、template 0／6）；全量 evaluation 81 秒（純 Python 單程序，每題最長約 1 秒，**預算遠沒用完**）。
- 架構：`src/arcagi/dsl/` 18 個網格原語（registry 一筆一個：名字＋參數推斷函式＋實作）＋2 個終端學習器（換色表、鄰域規則表，不佔深度）；程式＝JSON 列表 `[["split_overlay","v","xor"],["colormap",[[10,3]]]]`；`solvers/search.py` 逐層 BFS 到 3 步、觀察等價去重、參數從範例推、最短程式勝出；中間網格可用標記色 10。
- 軌跡：`--traces` JSONL 已存 training／evaluation 每題的全部過 train 程式（≤30）與近失敗（≤20）——**library learning 的原料已在手**（artifacts/r01/，本機有）。
- 量具：`arcagi eval [--traces]`、`arcagi compare`（逐題對照、新增／退步、按題型分組）、`--external "cmd {input} {output} {trace}"` 跨語言。

## 4. 第一輪失分在哪（隊長重算）

| 切片 | training | evaluation |
|---|---|---|
| **同大小（輸入輸出一樣大）** | 23/262 | **3/270** |
| 輸出比輸入小 | 23/101 | 14/94 |
| 有整條單色分隔線（格線盤面） | 12/77 | 7/77 |
| 過 train 但答錯（背答案） | 22 | 10 |

- **evaluation 的 270 題同大小只解 3 題**——這是最大的池子（training 題型：fill 123 題解 4、recolor 29 解 0、same_mixed 63 解 3）。同大小題大多是「逐物件」的事：依物件屬性（大小、形狀、顏色、是否碰邊、是否有洞）上色或刪除、物件移動／延伸畫線、補圖案。整張網格原語天生碰不到。
- 格線盤面 77 題：切成小格後要對小格做選擇（挑唯一不同的那格）、疊合、或把小格摘要成一個像素。r01 只有「切半」。
- 背答案：主要是「裁物件＋放大＋鄰域規則表」在小輸出上硬擬合。ARC 正式規則允許每個 test **2 次嘗試**，本量具目前只記 top-1。

## 5. 本輪求解器候選（r01 隊長建議，可組合）

## 6. aos 體系是什麼、能怎麼接（隊長讀過 proto8 docs、node-pool、kb-ideas 後整理）

**相關概念**（proto8/docs）：
- **資料夾＝程式**（C-68～C-70）：aos 只保證六個環境變數（`AOS_ENTRY`、`AOS_WS`、`AOS_STACK`…）和一支 `aos-exec [--ws WS] XXX [args]`；`XXX` 可以是檔、帶 `_entry` 的資料夾、或 `檔#/JSON指標`。被叫的程式有自己的 stack（預設 `$AOS_WS/.stack/`）。其餘全是慣例。
- 函數的 `_metainfo.json`（N-68）：說明、估的成本 `cost`（token／呼叫次數／時間）、逾時 `timeout_ms`；另有「他見的帳」`observed.jsonl`（實測用量）。不認得的 key 一律忽略（C-48）；**KISS 是最高原則**（C-56）；確定性（C-22）＝能寫死的節點換成程式，少走進 LLM。
- **本機已裝且實測可用**：`aos-exec`（隊長在 scratchpad 試過：資料夾＋`_entry` 腳本，stdin 傳得進、`AOS_WS`／`AOS_STACK` 有設）；另有 `aos-loop`、`aos-fsm`、`aos-daemon`、`aos-json`、`aos-llm`（問腦，要 llm-kernel daemon）、`aos-tools`、`aos-grow` 等。

**node-pool（想法 20，aos 使用者 11-08 已裁定的設計）**：
- 節點＝有 `_metainfo.json` 的定義資料夾；梯度＝投進節點 `_gradients.jsonl` 的一行信（誰、哪題、說什麼、分數）。
- 錢＝抽象分數（起步千 token＋秒/10，公式可改）。每批任務＝一個 epoch：頂層收「接受任務數×每任務價」，每層先報銷實際花費、利潤留 20%、80% 照**靜態引用次數**分給子節點；每節點每批扣房租；**連續 3 批 0 只列「建議退休」**，隊長按了才封存到 `defs.retired/`、可復活。檔：`pool/config.json`、`wallets.json`、`ledger.jsonl`（只追加）、`epochs/<n>.json`。
- **想法 21 壓縮**：規則被「同判決的更短規則」蓋住就標 `covered`、不刪（aos 試算 186→95 條有效、作答不變）；LLM 歸納本質每批 ≤1 次、≤2k token，只進 candidate。
- **想法 22 元優化**：改進「改進的過程」——aos 自己還在謝拉格語料上做，**不建議本輪碰**。

**對 arcagi 的對應**：積木（原語、學習器、巨集）＝節點；一次全量評測＝一個 epoch；「任務」＝一題，解出＝收入；被選中程式引用＝分紅依據；耗時＝花費；近失敗＝梯度信。

**接入選項**（可多選；隊長評估寫在後面）：

| 案 | 做什麼 | 成本 | 隊長評估 |
|---|---|---|---|
| **A1 積木資料夾化** | 每個積木一個資料夾 `blocks/<name>/`：`_metainfo.json`（說明、參數域、cost、kind=primitive／learner／macro、狀態 live／covered／retired）＋`_entry`（stdin JSON 網格→stdout 網格，可 `aos-exec` 單獨叫）。**搜尋仍 in-process**（逐步開程序會慢上千倍），registry 從資料夾樹讀 metainfo 對上 Python 實作；新積木（巨集）＝新資料夾、不改程式碼 | 中 | 最貼「資料夾＝程式」；巨集可以純資料（JSON 程式）不用寫 Python |
| **A2 求解器資料夾程式** | `aos/solver/_entry` 包 `arcagi` 求解一題；`arcagi eval --external "aos-exec … {input} {output} {trace}"` 跑一個小集合證明端到端 | 小 | 便宜的「真的接上」證據；全量用它會多開程序，只做小集合 |
| **A3 積木記帳（node-pool 簡化版）** | 每次全量評測＝epoch：解出題 × 價 → 依選中程式的積木引用分紅、扣房租（引用次數／耗時），寫 `pool/ledger.jsonl`、`wallets.json`；連續 3 epoch 0 → 建議退休（不自動刪）；近失敗寫進積木 `_gradients.jsonl` | 中 | 本輪只會有 1～2 個 epoch，退休不會真的觸發，但帳本骨架就位；可拿 r01 結果當 epoch 0 |
| **A4 壓縮／covered** | library learning 抽出的巨集若解題集被更短程式完全涵蓋 → 標 covered；live 積木同理 | 小（依附 S3） | 想法 21 的直接移植，跟 S3 綁 |
| A5 aos-llm 接 LLM 提案 | S5 經 `aos-llm` 而不是直接叫 API | 小～中 | 要 llm-kernel daemon 在跑，額度緊，可延後 |
| A6 元優化 | 改進「改進流程」 | 大 | 不建議本輪 |

## 7. 要規劃者決定的方向問題

1. 求解器範圍：§5 選哪幾案、先後；**驗收數字**（evaluation、training 下限與目標；每題時間上限）。
2. 物件層的規則怎麼表示、怎麼從範例推（屬性→動作的表？選擇器＋動作的原語對？），才不爆炸也不背答案。
3. 格線切塊做到哪（只有明顯分隔線？等分格？）。
4. library learning 本輪做不做、做多大（r01 軌跡只有 57＋21 題的程式）。
5. 背答案：要不要改量具加 top-2；top-1 仍為主分數？
6. **aos 接哪些**（§6 A1～A6）、接到多深；資料夾放哪（建議 `aos/` 或 `playground/` 在 arcagi 底下）；搜尋 in-process 與「資料夾＝程式」怎麼兩全。
7. 記帳的錢怎麼算（ARC 沒有 token 花費：用 CPU 秒？引用次數？）、一個 epoch 是什麼。
8. LLM 本輪碰不碰；碰的話量什麼。

## 9. 增補（11-08 12:05，第一次規劃與施工之後）：優化「產生積木」的過程

**使用者原話**（aos 轉達，wf/inbox/done/20261108T1205-aos-REQUEST.md）：「arc agi那邊，試試看“優化產生積木”這件事。積木的本質是模式匹配，模式難道只有這些幾何嗎？一段程式輸出true,json object，也可以算模式對吧，或是一個公式如x=y的2次方，這樣甚至可以超越大小」

aos 的白話理解（參考，非定案）：目標從「人手寫積木」轉成「**優化產生積木的過程**」——系統自己產生、評估、淘汰積木（同 aos 元優化、node-pool 一路）。積木＝模式匹配器，可分層：**判斷型**（謂詞 true/false）、**抽取型**（回 JSON：物件清單、計數、關係）、**關係／公式型**（數量、大小、位置之間的式子，與格子大小無關、能泛化）、**變換型**（現有）。用前三種「看懂」題目，變換型去「做」。要當第二輪主軸之一。

**本輪現況**（第一次規劃已施工完）：
- 已加：物件層（抽物件＋12 種屬性：顏色、大小、大小排名、形狀、碰邊、有洞、同形數…；選擇器＝「單一屬性等於某值」的謂詞，從範例推）、`object_colormap` 學習器（屬性值→顏色表）、格線切塊 4 原語、top-2、aos 積木資料夾（31 積木＋4 個自動抽出的巨集，帶 `_metainfo.json`）、node-pool 簡化帳（epoch 0 已記）。
- training 57→**79**（evaluation 結果跑中）。目前判斷型／抽取型其實已隱約存在，但**寫死在 Python**（屬性清單、謂詞形狀都是人手定）；積木產生只有「從過 train 程式抽高頻片段」一種（4 個巨集，量少）。
- 剩餘預算：帳號額度 >85%，本輪還能做**一個小施工單（約 1 條 opus 線、1 小時）**＋一次全量評測；大的放第三輪。

**要增補規劃決定的**：
1. 四型積木的**統一表示**（JSON 可序列化、LLM 可寫、能放進 `aos/blocks/<name>/`）：謂詞／抽取／公式各長什麼樣？跟現有變換型程式怎麼接（例：謂詞當選擇器、抽取結果當參數來源、公式定輸出尺寸或數量）？
2. 「**產生積木的過程**」本輪做哪個最小可量版本：例如 (a) 屬性謂詞的自動組合（AND／比較／排名），以「在 training 上能把變／不變物件分開的題數」評分、留高分、淘汰 0 分（接 node-pool 帳）；(b) 公式型：輸出尺寸＝f(輸入特徵) 的小式子枚舉（`h_out = a*n_obj + b`、`=n²` 等），用來剪枝或直接決定輸出大小；(c) 其他。
3. 怎麼評估與淘汰產生出的積木（用哪個 split、什麼分數、怎麼防背答案）；跟 node-pool 帳怎麼合（產生器本身也是節點？）。
4. 第三輪及以後的路線（元優化：優化「產生器」本身）。

**增補產出格式**：本輪小施工單（一段，可直接派給 1 條 opus 線：檔案範圍、介面、驗收數字）＋四型表示（每型一個 JSON 例）＋第 1～4 題推薦答案（各一句理由）＋第三輪起的路線。總長 ≤1200 字。
