### 1. 盲點與風險（量測雜訊、過擬合、成本、歸因）

- **量測雜訊錯置（假性 $\sigma=0$）**：`arcagi` 枚舉具確定性，在空基準上換 seed 或打亂題序幾乎必得 $\sigma=0$，使門檻退化為 `+1 題`。但元優化真正的雜訊來自 **200 題切分的離散抽樣變異**與 **`data_synth` 8 份子樣本的 50% 邊界波動**；在 $\le 8$ 組設定中取最大值配 `+1` 門檻，極易落入多重檢定的贏家詛咒。
- **過擬合與資料／狀態洩漏**：
  1. 線 A 若讓產生器在全量 400 題挖積木、僅在計分時切奇偶 200 題，偶數驗證題的結構已洩漏進積木庫。
  2. 線 B 拿 r05 改寫搜尋唯一有效的 **1～2 題**反推前景 IoU 門檻，屬 $n \le 2$ 看答案調參，毫無泛化保證。
  3. 空基準刪光產生器積木並在暫存目錄重跑，驗收卻要求 `formula_0832d6a3`、`extract_f23ec080`「仍 live」，未定義暫存樹如何與 `HEAD`（epoch 5）合併，導致實驗所測非最終上線狀態。
- **預算與時限自相矛盾**：§2 限定「線內只跑 $\le 50$ 題子集、每線 1 小時」，線 A 卻要求在奇偶共 400 題上跑滿 $\ge 11$ 筆（3 基準＋8 設定），且平行施工時尚無線 B 的省時門控（改寫搜尋耗時 $\times 3$），1 小時內必爆算力與工時。
- **歸因混雜與「假陽性攔截效應」**：「Python 先跑、無解才交 C++」意味只要 Python **過 train 答錯**（現有 eval 14 題／train 26 題），就會判定已解而**直接阻斷 C++ 補救**。A/C 增減積木會改變此攔截率；加上 `r05 HEAD + S1` 未先重測基準、三線合併才跑唯一一次全量，單靠 trace 記 `python/native` 看不見被 Python 假陽性搶走的 C++ 反事實正解，也無法拆解 A 與 C 在 BFS／投票中的交互影響。

### 2. 線 A 設計是否具資訊量？如何改才具決定性？

- **現有設計無論正、負結果皆缺乏決定性**：
  - **正結果可能是假象**：(1) `score_main` 要求「解程式含本產生器積木」，產生器只要吐出更短或排序更前的積木**取代原本純原語就能解的題**，總解題數 `+0` 也能刷高主分；(2) E1（調參）與 E2（合成集軟接）綁在一起缺消融對照，分不清是過濾器還是元優化奏效；(3) `generator_cut` 分紅「只記不決策」，即便正結果也未驗證 `aos` 帳本驅動假說。
  - **負結果亦無法證偽主軸**：(1) S5 證實背答案最嚴重的是 `pred`（多數不過率 50%、嚴格 81%），線 A 卻跳過調 `gen_predicates`，使 `extract/formula` 受制於劣質或被嚴格門檻清空的謂詞；(2) 在既有固定模板上只搜 $\le 8$ 個純量設定，測的只是「超參數敏感度」，且受限於主線深度 3／物件限第一步的求解器天花板，拿 `+0` 完全在意料之中。
- **改為具決定性（Decisive）的四項修正**：
  1. **三點消融**：固定切分明確對比 `預設無 E2` vs `預設＋E2` vs `meta 調優＋E2`。
  2. **改評「淨邊際貢獻」**：主分改為 $\Delta(\text{全庫通過合成集總解題數}) - \lambda \cdot (\text{過 train 卻不過合成集題數})$，杜絕靠搶奪既有解刷分，並直接對齊 `covered` 邊際分紅。
  3. **隔離產生集＋雙折交叉驗證（2-fold CV）**：產生器嚴格只在奇數 200 題挖積木、偶數 200 題驗證，再**奇偶對調重跑一次**；以配對題級勝敗（雙折淨勝皆 $>0$）取代無效的空基準 seed $\sigma$。
  4. **納入 `gen_predicates`**：把過擬合最重的謂詞納入實驗；若 E2 顯著降誤判而 E1 雙折淨增量仍為 0，即可決定性宣告「固定語法旋鈕觸頂」，r07 直接轉向結構變異。

### 3. 鑑於「表達力是瓶頸」，資源配置是否合理？更高槓桿的替代方案

- **配置失衡：主線 0% 資源投向表達力，且雙引擎語意斷裂**：
  - r04/r05 已反覆證實瓶頸在表達力，但規劃把三條線全花在**過濾與調旋鈕（A）**、**外殼包裝與無效搜尋門控（B）**、**搬運 34 顆既有規則（C）**，主線表達力幾乎零成長。
  - 更關鍵的是**組合斷裂**：E3b 僅做外部 fallback，`native/bin/solve` 不讀 `aos/blocks/`，Python 端又維持「物件限第一步＋深度 3」。凡需「S1 寬物件操作 $\times$ `aos` 產生積木」複合的題目，兩邊都解不出，「共用積木庫」並未發生。
  - 線 B 為「eval +0、耗時 $\times 3$」的改寫搜尋微調 IoU 門檻屬沉沒成本謬誤，直接預設關閉即可省下 67% 耗時。
- **不違背路徑約束的更高槓桿重配（維持 3 線 × 1 小時）**：
  1. **線 1（量測基準＋統一影子門檻，整併 B＋E2＋C 工具）**：改寫搜尋預設關；接通 `native` 混合入口，並對 **Python 自認解出的題（train ~121／eval ~52 題，極快）也跑一次 `native`**，直接抓出 Python 假陽性攔截了多少 C++ 正解；實作單一「合成集影子驗證器」供全線共用，免 A/C 重複開發並順手收進 S2 候選。
  2. **線 2（呼叫鏈／子樹巨集蒸餾，直擊表達力與使用者主軸）**：唯讀呼叫已上線的 `dsl/ext/`、`objrule/families/`（S3）並從成功 trace 抽取高頻多步呼叫鏈，封裝為帶槽巨集 `m_*` 進 `aos/blocks/`。將 2～3 步物件／選擇器呼叫鏈壓成單顆積木，**不必改求解器就能在深度 3 內突破「物件限第一步」瓶頸**，正面落實「呼叫鏈空間轉換」與「子樹即積木」。
  3. **線 3（離線覆蓋矩陣之元優化）**：先一次算出各積木源（三產生器、S2、S3、新呼叫鏈巨集）在訓練集與 `data_synth` 的覆蓋矩陣，讓 `_meta` 在秒級離線迴圈中優化 `generator_budget` 配比與准入門檻（含雙折驗證），1 小時內穩健跑完。

### 4. 驗收門檻是否合理？

- **總分門檻偷換基準（`evaluation >= 42` 實為零增量）**：簡報 §7 原建議 `>= 42（主線自己）`，規劃卻改成 `>= 42（混合入口）`。但 S1 在 r04 早已達 42，等於三線合計淨貢獻 `0`（甚至微退）也能過關。應要求**相對同 commit `HEAD` 混合基準具正增量**，並同時單列 Python 獨立分數與雙邊重疊數。
- **誤判門檻過鬆（`過 train 答錯 eval <= 14 / train <= 26`）**：`14/26` 只是維持 r05 現狀。既然 E2 專治背答案（且降低 Python 假陽性能直接釋放題目給 C++ 補解），應要求 **train 誤判實質下降（例如 `<= 20`）**；若毫無下降，即暴露「有收入舊積木豁免退休」放生了假陽性元兇。
- **線 A 內部指標自相矛盾且易被刷分**：
  - **前後衝突**：§2 驗收允許新上線 `pred` 合成集多數不過率 `<= 30%`，§3 影子門檻卻規定「`pred` 要全部過（不過率 0%）」；空基準刪光舊積木也與「兩顆舊積木仍 live」衝突。
  - **統計與分子漏洞**：$\sigma=0$ 時 `+1 題`＋偶數集 `>= 基準（允許 +0）`極易靠隨機波動達標；不過率 `<= 30%` 未設最低上線顆數，只收 1 顆平庸積木即過關；硬性要求 `meta 帳 >= 11 筆` 則在 1 小時限額內鼓勵湊低品質實驗。
- **線 B／C 門檻誘因錯置**：線 B「改寫搜尋耗時降 $\ge 50\%$」仍保留一半無效耗時，不如直接預設關閉（耗時降 ~100%）；線 C 硬性要求「進帳 $\ge 1$ 顆」會在 34 顆皆重複或背答案時逼人放水，應改驗**影子預核對 S5 已知好／壞積木的區別率**，入庫數允許為 0。
