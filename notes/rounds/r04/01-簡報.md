## 1. 目標與使用者前提（原話整理）

- 使用者：「就是拿我們這套 aos 體系去嘗試解 arcagi」。**符號邏輯**解 ARC-AGI-1；LLM 只用來找規則、寫程式、蒸餾，最終解題靠確定的程式；**神經網路盡量不用**。可暴力吃 CPU、可寫 CUDA（RTX 5060 Ti 16GB）。
- 主軸（使用者 11-08 12:05 原話）：「試試看“優化產生積木”這件事。積木的本質是模式匹配，模式難道只有這些幾何嗎？一段程式輸出true,json object，也可以算模式對吧，或是一個公式如x=y的2次方，這樣甚至可以超越大小」。另一主軸：**用 aos 體系**（積木＝資料夾程式、node-pool 記帳、covered 壓縮、元優化）。
- 使用者也鼓勵**大量吃 CPU 的暴力搜尋**或 CUDA（在限制內）。目前全量評測只要一兩分鐘、每題最長 3.8 秒（預算 5 秒），算力遠未用滿。
- 方向問題不停線：隊長代定、記代定清單，使用者回來翻案。

## 2. 不可違反的約束

| 約束 | 說明 |
|---|---|
| 成績以 **evaluation 400 題**為準 | training 有 re-arc 現成解答（洩漏風險），只當開發集；**產生／評分積木只能用 training** |
| 不用神經網路；**不新增 Python 依賴** | 純 stdlib（無 numpy）。C++／CUDA 可另開子資料夾經 `--external` 接 |
| 機器安全 | CPU 批次 `nice -n 19`、≤12 worker、單批 ≤16GB、顯存 ≤12GB、swap 512MB；同時只跑一條全量評測 |
| 額度緊 | 本輪約 **3 條 opus 線×1 小時**＋全量 training、evaluation 各一次為原則；aos-llm 要額度 |
| aos repo **只讀** | 在 arcagi 的 `aos/` 試驗場做；不跑 install.sh |
| 程式碼規矩 | `src/arcagi/<領域>/`，單檔 >300 行拆（`blocks/pool.py` 302 行，本輪順手拆）；pytest；退步列原因 |

## 3. 現況（r01～r03 已有）

- 成績：**evaluation 32/400**、training 86/400（r02 28／79），退步 0；過 train 但答錯 evaluation 13。
- 搜尋：逐層 BFS 到 3 步（`MAX_DEPTH=3`、`TIME_BUDGET=5s`、`MAX_NODES=20000`）、觀察等價去重、參數從範例推、最短程式勝出、收完第一個有解深度投票；終端學習器（換色表、鄰域規則、物件換色表）不佔深度。
- 積木四型（共用外殼 `{"kind":pred|extract|formula|transform,"in","out","body"}`，body＝S 式 JSON），全在 `aos/blocks/<名>/`（共 ~300 個資料夾）：

## 4. 失分在哪

| 切片 | evaluation | training |
|---|---|---|
| 同大小 | **8/270** | 37/262 |
| 輸出比輸入小 | 17/94 | — |
| 其他（變大／混合） | 7/36 | — |
| 尺寸隨輸入、非倍數 | 6/54 | — |

- **同大小 270 題是最大池，三輪幾乎沒動**。r03 C 線抽查 training 53 題「謂詞分得開變／不變物件但沒解出」：多數是**每個物件各自規則**——各物件移動方向不同（朝最近同色物件／朝牆）、換成鄰近物件的顏色、依大小決定新色、混色重繪。現行「一個選擇器＋一個固定參數動作」表達不了。
- 抽取積木 evaluation 0 題：只接了裁／塗／留／計數，用途太窄。
- 投票無效：第一個有解深度幾乎只有一種輸出。

## 5. 本輪候選（r03 隊長建議；**供選擇、非定案**）

| 案 | 內容 | 預期 evaluation 增量 | 跟主軸的關係 |
|---|---|---|---|
| D1 每物件各自規則 | 動作參數改成「從該物件抽出的值」：新顏色＝f(物件屬性)（鄰近物件色、大小排名→色表、接觸色）、移動方向／距離＝朝最近物件／牆／同色物件、延伸方向＝物件屬性；抽取型積木當**每物件參數來源**；擬合＝對所有 train 物件一致 | +3～8（同大小） | 抽取型積木真的接到動作 |
| D2 抽取×公式組合、產生器深度 2 | 公式的 x 可以是抽取值（例：輸出高＝最大物件的格數）；式子 2 層（`a·x+b·y`、`(x+1)·y`…），在 training 評分、covered 壓縮 | +1～4 | 「公式超越大小」再推一步 |
| D3 帳的預算真的執行 | 依 `generator_budget` 分配各產生器枚舉額度（候選數或秒數），下一輪重算；產生器表現差 → 額度降 | 0（結構） | **元優化第一步**：優化「產生器」本身 |
| D4 加大搜尋預算 | 算力只用到一兩分鐘：深度 3→4、節點 2 萬→20 萬、每題 5→30 秒、或 C++／CUDA 枚舉；配尺寸提示剪枝 | +1～5（不確定，也可能增背答案） | 使用者鼓勵吃 CPU |
| D5 aos-llm 小樣本 | 20 題未解題，LLM 寫四型 JSON → 執行器驗 train，量通過率；四型執行器已齊 | 量測用 | 「LLM 找規則、程式驗證」；**額度緊** |
| D6 投票變有用 | 有解深度後多看一層，或讓不同學習器產生替代輸出 | top-2 +0～3 | 降背答案 |
| D7 拆 `blocks/pool.py` | 302 行，拆記帳／產生器預算／CLI | 0 | 規矩 |

- 公開經驗：icecuber 式手寫 DSL（約 140 變換、深度 3～4、C++）私有約 20%；公開 evaluation 上 DSL 搜尋一般 10～25%。

## 6. 要規劃者決定的方向問題

1. 本輪範圍：§5 選哪幾案、先後、分幾條線（≤3 條同時、按檔案切）；**驗收數字**（evaluation、同大小、training；每題時間；過 train 答錯上限）。
2. 「每物件各自規則」怎麼表示與擬合：參數來源有哪些（抽取積木？鄰近關係？）、怎麼從 train 擬合（每物件對應→找一條共同規則）、怎麼接進搜尋與四型 JSON、怎麼防背答案。
3. 能不能把「每物件規則的參數來源」也交給產生器枚舉、由帳評分（讓它也是「產生積木」而非人手寫死）。
4. 公式產生器加深到 2 層＋抽取值當特徵：枚舉空間怎麼控、covered 怎麼算。
5. 帳的預算要怎麼「真的執行」：額度單位（候選數／秒）、下限、誰來調。
6. 搜尋預算加大到多少（深度、節點、秒）；要不要 C++／CUDA；怎麼防加大後背答案變多。
7. LLM（D5）本輪碰不碰；碰的話量什麼、上限幾題。
