**讀法**：規劃者**只讀本檔**就要能定第一輪範圍、方法、驗收數字；不需要、也不應該去廣讀 repo。本檔的事實都已核過（數字來自 `docs/inventory/training-features.csv` 與現有報告）。

## 1. 目標與使用者前提（原話整理）

- 目標：用 aos 體系（符號邏輯）解 ARC-AGI-1。每題給 2～10 組 input→output 範例（多數 3 組），要對 test input 產生**完全正確**的輸出網格（top-1 exact match，整題所有 test 都對才算）。
- 使用者原話：「就是拿我們這套aos體系去嘗試解arcagi。」「因爲是純粹邏輯判斷……他那邊可以盡量多寫程式，包括用暴力解大量吃cpu，或是寫cuda程式(我有裝)。神經網路盡量不要，他那個有不確定性。」「他那邊其實可以直接開始試試看了。跟我們這邊的輪次一樣。」
- 長期路線（使用者 11-07 晚）：純 LLM 是錯的路；ARC-AGI-1 是「智能種子」。**LLM 只當出入口與輔助**（找規則、寫程式、蒸餾），最終解題靠確定的程式；把 LLM 解題的過程沉澱成可重用的規則／程式，種子長大後能自我吸收、遞迴改進。
- 方向問題不停線：隊長代定、記 `代定清單.md`，回報時給使用者翻案。
- 第一輪範圍小（aos 原話建議「挑一類容易寫成規則的題」）。

## 2. 不可違反的約束

| 約束 | 說明 |
|---|---|
| 成績以 **evaluation 400 題**為準 | training 400 題有 re-arc 現成 DSL 解答（洩漏風險），training 只當開發集 |
| 不用神經網路 | 規則、搜尋、暴力枚舉、CUDA 都可以 |
| 不新增 Python 依賴 | 專案目前**零依賴**（純 stdlib，連 numpy 都沒裝）；要依賴得問使用者 → 第一輪純 Python，或另開 C++/CUDA 子資料夾走外部程式介面 |
| 機器安全 | CPU 批次 `nice -n 19`、≤12 worker、單批 ≤16GB、顯存 ≤12GB、swap 只有 512MB；**同時只跑一條全量評測** |
| 額度緊 | 帳號本週已用 >81%：第一輪要能在少量 agent 工時內做完，不重複跑全量 |
| 程式碼規矩 | 模組放 `src/arcagi/<領域>/`，單檔 >300 行要拆；pytest 測試；commit 附 evaluation 改前／改後題數 |

## 3. 現有量具（已完成，直接用）

- 求解器介面：Python plugin `module:function`，收 `SolverTask`（`train` 範例、`test` 輸入、`Grid`＝tuple of tuples，值 0–9），回傳預測清單或 `SolverResult(predictions, trace)`。也可外部程式（任何語言，JSON 檔進檔出，`arcagi eval --external "cmd {input} {output} {trace}"`）。
- 評測：`arcagi eval --split training|evaluation --solver X --timeout S --output R.json --traces T.jsonl`。**逐題序列執行**（每題可獨立程序＋逾時），沒有內建平行；400 題 × 每題 3 秒 ≈ 20 分鐘。
- 嘗試軌跡 `arcagi-trace/1`：每題記 attempts（description、program、train_results、selected、耗時、reasoning、data），`TraceRecorder`＋`check_on_train` 是現成 helper。`--traces` 輸出把軌跡和對錯接在一起，是日後蒸餾的原料。
- 比較：`arcagi compare base=A.json new=B.json --labels training-features.csv --label-column category`：逐題對錯、新增解出／退步、按題型分組。
- 基線：identity 0/400（兩個 split）；template（只試整張網格 5 種對稱）training 6/400、evaluation 0/400。

## 5. 參考庫（只讀）裡相關的東西

（由 sonnet 雜活摘要，隊長篩過；路徑都是唯讀參考。）

**aos 體系**（`~/repo/simple_tools/aos/proto8/docs/` CONCEPTS／NORMS／CONVENTION）：
- 資料夾＝程式（C-68）：一個資料夾有入口可執行檔，像 lisp 的 list；aos 只保證幾個環境變數與 `aos-exec`，其餘是慣例。
- **確定性（C-22）**：把 S 表示式拆開，能寫死的節點換成程式，減少走進不可預測（LLM）節點的機會——這正是「DSL 程式取代 LLM 判斷」。
- aos 函數和 tool 呼叫可互轉（C-82）；KISS 是最高原則（C-56）；規範比實作重要（C-45）；不認得的 key 一律忽略（C-48）。
- 可套用：一個 DSL 原語＝一個可獨立執行的單元；求解流程串成狀態機；LLM 只在入口（看題提假設）和出口（蒸餾）。

**蒸餾／節點池／元優化**（`proto8/thinking/2026-11/07/kb-ideas/README.md`、`.../08/node-pool/`）：
- 想法 17：「蒸餾 LLM 為固定符號邏輯」，老式專家系統的事，現在有 LLM 可再試。想法 21：蒸餾後還要**壓縮**（被更短規則蓋住的標 `covered`）。想法 22：元優化＝改進「改進的過程」。
- 節點池：節點＝資料夾＋`_metainfo.json`；用抽象分數（token＋秒數）做分紅／房租，連續 0 分只建議退休——可對應「DSL 原語庫的使用率記帳與退休」。
- 使用者原話：「arc agi 1就是在此時加入進來的，這是種子，後面會慢慢成長直到能完全代替LLM作爲思考驅動。」「所謂蒸餾成符號邏輯，就是嘗試從現在的聰明高階LLM蒸餾出智能種子，等到其成長到能自我吸收營養進行RSI」「可能還得先把arc agi 1解決個七七八八」。

**progsynth_cpp**（`~/repo/machine_learning/progsynth_cpp`，C++17 零依賴，整數算術 DSL，無 ARC／網格）：
- 依大小 bottom-up 枚舉（回傳最小解）＋**觀察等價（OE）剪枝**：以「程式在所有範例輸入上的輸出向量」當簽章去重，候選數降到 33～71%；型別導向剪枝；GP 與 top-down 對照框架。
- 直接可搬：OE 改成「在所有 train 輸入上的輸出網格簽章」；缺的是網格型別、物件抽取、庫學習。

**論文**（`~/repo/paper_readings/summarize/`，索引 `index/cat_e.md` 有 25 篇 ARC 類）：
- GridCoder（2411.17708）：ARC 程式誘導，DSL 搜尋＋學習排序。ARCANA（2607.09059）：物件場景圖、typed DSL、符號執行與失敗歸因。
- SOAR（2507.14172）：LLM 產候選程式、符號執行驗證、自我改進——蒸餾資料來源的迴路。
- CompressARC（2512.06104）：MDL（最短描述）當推論準則——可當多解時的排序（選最短程式）。
- DreamCoder（2006.08381）、Stitch（2211.16605，庫學習快 3～4 數量級）、babble（2212.04596，e-graph 去同義）、AbstractBeam（2405.17514，庫臃腫是負債）：**library learning**——從解出的程式中抽共同片段成新原語，是「蒸餾＋壓縮」的現成藍本。

## 7. 要規劃者決定的方向問題

1. 第一輪範圍：上表選哪案（或組合），以及**驗收數字**（evaluation 至少幾題、training 至少幾題、每題時間預算）。
2. 符號規則怎麼表示：Python 函式組合（名字串成程式字串存軌跡）？還是小型 S 式 DSL（可序列化、可被 LLM 寫、可被 C++ 重新實作）？
3. 搜尋策略：逐層枚舉＋觀察等價剪枝（同輸出就去重）？還是按題型分派（先分類再搜）？參數（顏色、倍數）怎麼從範例推，而非盲枚舉？
4. 多解時怎麼選（多個程式都過 train）：最短？最先？投票？
5. 軌跡怎麼記才能蒸餾：記全部嘗試還是只記過 train 的？記 DSL 程式字串＋題目特徵？
6. 怎麼從 LLM 蒸餾（本輪不一定做，但要定方向）：LLM 看題寫 DSL 程式 → 程式驗證 → 成功的程式片段沉澱成新原語（library learning）？
7. 語言：第一輪純 Python，還是直接上 C++／CUDA？
8. 程式放哪：`src/arcagi/solvers/` 下新模組（例如 `src/arcagi/dsl/`＋`src/arcagi/solvers/search.py`），還是 arcagi 底下獨立試驗場資料夾？
