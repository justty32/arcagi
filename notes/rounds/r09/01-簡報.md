## 4. Argon 審 v3 的重點（詳 02b）

1. 失蠟死鎖：stop 才鑄 1 題，卻要 ≥3 個蠟模才能反合一 → 前兩次 stop 必空轉。**與裁定 (1) 相容的解法候選**：蠟模跨 epoch 累積在 `foundry/wax/`，湊滿 3 個同型（殘差指紋相近）才進鎖；或單蠟模走「逐段擬合」路徑，擬合出的段本身就是可以單獨過 MDL＋留一的 comb 候選（不必等反合一），只是先進 `incubating`。
2. 觸發矛盾：§三.1 只在 stop 鑄模，§三.6 卻把鑄模列為 UCB 常規臂 → 照裁定 (1)，鑄模移出 UCB，只由 stall=stop 觸發。
3. LLM 黑盒 Python 沒有中間態 → 強制 `step(tag, grid)` 檢查點。
4. 對手鍛造會被不可解壞題鎖死 → 能力邊界方差權重＋非退化門。
5. UCB 即時獎勵餓死縱拆與鑄模 → `parent_route` 延遲分潤。
6. bisect 遇累積效應誤殺 → 只對本輪新轉正差集做消融，先查 ledger 單列邊際帳。
7. 審查節點仍寫死 → `kind:sieve`（觀測等價吸收律剪枝）等「可搜尋的審查列」。
8. LTO-SCF 分母截斷偏誤 → 在聯集上以超時上限代入。
另：鑄模成本要進橫軸；`null` 多的見證會假命中（`info_bits` 下限）；6 個手寫逆推器對新 comb 無效（商空間投影）；活樹要有 `live/` 即時投影與 `events.jsonl`。

## 5. 活樹（意見 7）的落地要求

- 位置 `~/code/playground-arc1/ws/hammer/`（目前不存在，r09 建立）；程式在 `src/arcagi/hammer/`。
- 使用者能：`cd` 進去 `ls` 看節點資料夾、跑 `_view.sh` 看狀態與殘差色塊、對節點發訊息（v3 B2 `ctl say` 寫進節點信箱，引擎下一 pass 讀）。
- 若有常駐程序（daemon），必須能乾淨停止（例：`ctl stop` 或刪 `RUN` 檔，下個 pass 邊界退出），README 寫清楚怎麼看、怎麼停。沒有活樹在跑時資料夾仍可看。
- 鑄模廠的 LLM 呼叫：本 repo 的 LLM 就是 Claude 子 agent（S2 做法）。活樹不能自己開子 agent，建議由活樹寫「鑄模請求」到 `foundry/requests/`，隊長派一個 opus 子 agent 照題寫帶檢查點的 Python 解一題、只留軌跡。這樣 `solve/` 的 `llm_calls` 仍為 0，LLM 並行 ≤2 也守得住。

## 6. 硬限制

- aos 體系、符號邏輯、無神經網路；可多寫程式、暴力吃 CPU、可 CUDA（≤12GB 顯存）。
- 批次 `nice -n 19`、workers ≤12、單批 ≤16G（`systemd-run --user --scope -p MemoryMax=16G`）；swap 512MB；Python 跑 1M 節點時 workers 要少（6 workers 超過 8G）。
- 全機同時只跑一個全量 eval；子 agent 同時 ≤3；不開 codex。
- 純度：空樹不 import 舊樹（`scripts/r07_purity.sh`）；holdout（H8、H24）只量不學、agent 不准讀題。
- 時間：本輪以「半天內收輪」為度。r08 一條 8-pass Python 曲線 4～9 分鐘；換 arcbatch 後應降到 1 分鐘內。
