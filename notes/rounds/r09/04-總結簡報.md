## 1. 結論先講

- lv1 錘子造出來了，而且是活的：`~/code/playground-arc1/ws/hammer/` 是一棵資料夾樹。本體、審查（G1 門、原語剪枝）、改進（睡眠造詞、拆法、路由、鑄模）都是 `ops.jsonl` 的列，由樹自己的判準在 incubating、live、dormant 之間升降。可以 `cd` 進去用 `_view.sh` 看，用 `./ctl say|pause|weight|add-op` 發訊息，刪 `RUN`（`./ctl stop`）就會在下一個 epoch 邊界停。
- 主樹 AUC_L **40**，不學的對照是 32，靜態手寫拆法是 48。H24 1→2，每個 epoch 都沒退，熔斷 0 次。H8 0，llm_calls 0，false_pos 0。M0（重現 r08 sha）過。
- **方向判準 M2 四中二：字面上過 (a)、(b)，但 (b) 要打折。** (a) 樹自己升了睡眠造詞積木，帶新解題和 H24 +1。(b) 路由表被 layer-2 掃描接受，但多解的題來自 r08 手寫的 halves，而且只寫在暫存樹上。(c)（真蠟模產出 comb）和 (d)（贏過靜態拆法或 H8 +1）都沒過。
- 最大的新發現：**真蠟模三段一段都擬合不到**。LLM 寫的步太粗，例如「按物件大小重塗」，空樹的 32 個 list 原語在 200k 內寫不出來。失蠟法的管線是通的，但料跟語言對不上。r10 的頭號題目就是這個。
- evaluation 沒有重量：r09 沒動求解入口（gated），仍是 r08 的 56/400。

## 4. 活樹怎麼看、怎麼干預

```sh
cd ~/code/playground-arc1/ws/hammer
./_view.sh                    # 狀態、最近 epoch、各狀態列數、最近事件
./ctl status | ops | ledger --tail 20
./ctl say solve "你好"        # 下個 epoch 邊界讀，回覆在 nodes/solve/outbox/
./ctl pause grow ; ./ctl resume grow
./ctl weight route_ok_rt_sleep 3
./ctl add-op '<json 列>'      # 進 incubating，走同一判準
./ctl run --epochs 12 --daemon   # 背景跑（nice 19）；./ctl stop 刪 RUN，下個邊界停
```

- 現在**沒有常駐程序**。樹停在 epoch 8，`RUN` 檔還在，但 daemon 已經結束。
- 停止有實測：在暫存副本上跑 `ctl stop`，引擎跑完當前 epoch，在下一個邊界寫 `stopped` 事件後退出（約 40 秒）。修了一個 bug：`ctl run --daemon` 多包了一層 `setsid`，`daemon.pid` 因此指錯程序，`status` 會說「not running」。
- 說明書：`~/code/playground-arc1/ws/hammer/README.md`。

## 5. 得失

**得**
- 錘子的三種部件第一次都變成可以被搜尋、可以升降的資料列，也有了凍結的判準和 H24 熔斷。意見 6 有了骨架，意見 7 能實際操作。
- arcbatch 後端讓 epoch 從分鐘級降到秒級（不含 halves 時 1～9 秒）。
- 樹自己長出、自己升級的積木帶來 H24 +1，而且沒有退步。

**失**
- 失蠟法的料跟語言對不上：LLM 用「物件」「外圈」這種概念切步，空樹語言寫不出來，三段全成斷裂面。
- 審查被搜的結果幾乎都是 0：gate 參數在現行引擎裡多半沒作用，原語剪枝在折外都會掉題。唯一被接受的路由變更，靠的是手寫拆法。
- halves 一升 live，整棵樹就退回 Python，慢了 8 倍。
