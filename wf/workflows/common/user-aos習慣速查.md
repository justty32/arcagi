## A. 今晚整夜最用得上的（前五條）

1. **他睡著時一句都不要問，也不要停下來等他。** 原話（11-07）：「這段期間不可以問我問題。除此之外，有需要我決策或給意見的話，可以在那個npm run dev的網頁放東西，我有空會看。」照做：要他拍板的，放上看板的「待你裁」，附**預設選項＋後果**；這條線先照預設往下做，他回答後再改。做錯可以改回來，停線才是浪費。出處 aos:workflows/common/user/01-說話授權與記憶.md「出門／不在時」「額度緊時」。
2. **06:20 起床報告的格式。** 他回來的問法是「跟我說說這段時間發生了啥、你做了哪些大決定」。照做：①一兩句講結論（成了什麼、沒成什麼）②代定清單，每條寫上「在哪裡可以翻案」③要他裁的題目最多五題、每題附推薦。手機上看的頁面照他 11-08 的原話：「細節折疊，然後盡量ELI5風格講述。圖不用多，因爲artifact承載力有限。盡量只講結論就好，中間過程除非很重要否則不用附。」出處同上，以及 aos:workflows/common/user.md 表格的「artifact／說明頁風格」那一列。
3. **講人話，具體寫法。** 09-01 他講了兩次「講人話」「跟我說話請用白話」。他的強項在構想，不在 CS 術語；**密度很高、好幾條線互相交叉引用的總結他讀不動，會退回來要你重講**。照做：用完整句子，一段只講一個重點；術語第一次出現時用日常比喻帶過；編號引用（D-r7-13、N2、M4）點到就好，**不要讓他回去查表**。技術深度不用降，要降的是表達方式。出處 aos:workflows/common/user/01-說話授權與記憶.md「說話方式」。
4. **「不如…？」「幫我想想」是要討論，不是叫你派工。** 11-09 晚他說「用 aos 知識庫去搞」amber_sword，aos 頂層當成決定直接派了隊長，只好馬上停掉。照做：先回想法和選項，**等他說「開工」或「做吧」再動手**。出處 aos:HANDOFF.md 11-09 22:3x 那條的第 2 點。
5. **大方向是他的，你只做兩件事：挖邊緣狀況、快速做原型給他試。** 這是 aos 鐵律 5。發現的問題攤給他、由他判斷，**不要拿你自己的大方向去換掉他的**。他沒回應的邊緣狀況（09-01 他自己定的通則）就當成「本來就有的差異」或「實作時自然會解決」，**不追問、也不列待辦**。另外，像「判官睡著」這類問題，他說「這是使用者在設計系統時要承擔與管理的風險」，所以不用為這種事加防護。出處 aos:../AGENTS.md 鐵律 5、aos:workflows/common/user.md 表格下的引言、aos:session_logs/2026-11/2026-11-07.md。

## B. 確認邊界與問法

- **不要一題一題問他。** 原話（10-19）：「為何你要一直問我呢？為何你不去讓fable去規劃呢？……proto8的相關原則和我們現在要做的東西有衝突時，你為何不告訴我呢？」照做：細節交給 fable 照原則自己定。要帶給他的只有兩種：**跟既有原則衝突的地方**（哪一條、衝突在哪、各自的後果）和**原則推不出答案的方向題**。出處 aos:workflows/common/user/03-討論紀錄與規劃.md。
- **他說「不想看」的時候，用實測代替拍板**：先跑出數字再給他看。出處 aos:workflows/common/user.md「回覆風格」那一列。
- **「讓大家喘口氣」指的是 barrier**：各線收拾好、同步完進度再繼續，**不是停工**。出處 aos:workflows/common/user/03-討論紀錄與規劃.md。
- 他人不在、手頭的事做完時，他喜歡你**繼續挖邊緣狀況**。11-05 原話：「剛吃飽，想午睡...你繼續多測試一些邊緣狀況吧。」出處 aos:session_logs/2026-11/2026-11-05.md。

## C. 派工與模型（補你 wf 沒寫到的）

- **頂層不親手做事。** 09-24 原話：「你不要自己做事，盡量交給 agent」。想「順手」做點小事之前，先問自己能不能一句話交給別人。出處 aos:workflows/dispatch/aos-teams.md「誰做什麼」。
- **codex 會做到一半就說做完了。** 原話：「他會做到一個階段就停下來說自己做完了。這需要你去設定/goal。」照做：提示的第一行寫 `/goal <一句可以驗證的完成條件>`，任務書從 stdin 給。出處 aos:workflows/dispatch/aos-teams/02-指令沙箱與試玩.md。
- **碰程式邏輯要小心 sol。** 11-07 他說「gpt-sol的程式能力實在太差」，那天改成 opus 自己寫碼。sol 交回來的 diff 一定要由 opus 審過；它越界改到的檔要還原。出處 aos:session_logs/2026-11/2026-11-07.md。
- **改寫他的概念或規範條文，不算簡單工作**，不派 sonnet/terra。10-19 原話：「竟然是開sonnet做事...不怕錯嗎」。出處 aos:workflows/common/user.md「子 agent 模型」那一列。
- **Argon 用 headless（-p）跑的時候**，一要讀檔就會因為沒人批准而空手結束。照做：不加 skip-permissions，把要審的文字全文貼進提示，並寫明「不要用工具，直接依文字作答」。出處 aos:workflows/dispatch/aos-teams/05-同機session與Argon.md。
- **每做完一段就派人試玩。** 原話（09-13）：「每次做完一個段落都可以讓他們去玩玩看，給建議，然後我們改進。」派一個只拿到 README 入口的 agent 去用、去弄壞，回報難懂的地方。出處 aos:workflows/dispatch/aos-teams/02-指令沙箱與試玩.md 末段。

## D. 寫東西、命名、收尾

- **改條文時舊句直接刪**，不留刪除線，也不寫「原句照留」；要找回來靠 git（11-07 檢討第 2 點）。出處 aos:workflows/common/user/03-討論紀錄與規劃.md。
- **討論紀錄只留三種東西**：他的原文（整理過的）、決策結果、討論出來的結論；整份都是 AI 寫的過程就整份刪。出處同上。
- **日誌少寫**：每條一行「動了哪些檔、做了什麼」，再連到結論所在的地方；結論寫進它該在的文件，不寫在日誌裡。出處 aos:workflows/common/user/02-交接與收工.md。
- **命名要讓人一看就懂。** 他嫌 `AOS_KERNEL= aos-agent ctl wake --target 名字` 醜。旗標名他要能表達意思，原話：「因為單restart，你不知道他想表達的意思。」出處 aos:session_logs/2026-11/2026-11-07.md、2026-11-06.md。
- **他說「審」的時候也要審設計**：冗餘、該考慮卻沒考慮到的狀況（規模、當機後怎麼恢復、權限、人工介入）、跟自己宣稱的原則打架的地方。報告分成必修／設計問題／建議／要他裁四類。出處 aos:workflows/common/user/02-交接與收工.md「審的範圍」。
