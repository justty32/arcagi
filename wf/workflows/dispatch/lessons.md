# 派線踩過的坑

[dispatch](README.md)｜[WORKFLOWS](../../WORKFLOWS.md)

多數是同一位使用者在 aos 專案實跑後長出來的，挑出跟 arcagi 相關的；**下一份交接書送出前對一次**。arcagi 自己踩到的往後追加。

## 1. 預掃要涵蓋全部組別

派線前便宜的預掃（檔名、大小、題目 id）常讓工作量掉一個數量級；但漏掃的那組會在收線時才爆。交接書要嘛把預掃做完，要嘛明寫哪幾組沒掃過。

## 2. 線推翻交接書時要接受

線回報「交接書寫的三個其實只有兩個，理由是……」通常是線對——它手上有實測資料。驗收條數寫死是防亂加驗證，不是要它湊數造假；改交接書，別叫它重跑去補齊。

## 3. 背景與工作步驟不可互相矛盾

背景寫「可以原樣複製」、步驟卻寫「佈局零改動」，線只能二選一。送出前對照一次，衝突處寫死哪個為準。

## 4. 整檔改寫用單一操作，不拆成刪＋加

中間檔案真的不存在，別的線會掃到、崩潰時會留下缺檔的工作樹。每批邊界跑 `git status --short | grep -E '^(D |.D)'` 要零命中。

## 5. 合併成功之後才刪分支／worktree

合併指令單獨跑、看退出碼（`| tail` 會吃掉退出碼）；主 repo 有使用者未提交改動時先比交集。

## 6. worktree 起點可能很舊

Agent 工具的 worktree 不保證從 main HEAD 開；worktree 線第一步確認 `git log -1` 與主 repo 的 main 一致才開工。

## 7. 任務書要明講的幾件事

：commit 署名照抄交接書給的那行（不是環境提醒裡的）；真跑次數與時間上限一開始就限；臨時檔放 scratchpad 裡自己的子資料夾（多線共用 scratchpad）；共用檔（SESSION-LOG、WAIT_USER、ledger）只准一條線碰。

## 8. 成熟元件原樣沿用，不派人重寫

已經可用的模組（載入器、評分、實驗 runner）任務書直接點名「沿用、只改最小差異」，它們的既有規則不列待問。

## 9. 「故意改壞再還原」驗證測試時，Python 可能沿用改壞版的快取

同一秒內改壞又還原、大小相同，`__pycache__` 不會失效。跑測試加 `python -B`，或還原後 `touch` 該檔。

## 10. 數「有幾份評測在跑」別用 `pgrep -fc`

它會把含該字串的 shell、等待迴圈都算進去；用「命令列開頭就是那支程式」的比對法。
